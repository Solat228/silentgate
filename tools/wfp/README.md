# Откуда взяты числа в `app/lib/engine/windows/wfp_layout.dart`

Раскладка структур Windows Filtering Platform и значения GUID **не выведены по памяти**.
Их печатает `wfp_layout_probe.c` — программа на C, собранная компилятором MSVC против
заголовков Windows SDK (`fwpmu.h`, `fwptypes.h`) с помощью `offsetof`/`sizeof`.

Зачем такая строгость: ошибка на четыре байта сдвигает поле `flags` у `FWPM_SESSION0`,
сессия из **динамической** становится статической — и фильтры переживают смерть процесса,
оставляя машину без интернета. Ни тесты, ни глаза такого не видят.

## Как перепроверить

```
tools\wfp\build.bat
```

Скрипт задаёт пути к MSVC и SDK явно (`vcvars64.bat` на машине владельца падает: `vswhere`
не находится), собирает `probe.exe` и печатает таблицу. Сверять её с константами в
`wfp_layout.dart`; тест `app/test/wfp_layout_test.dart` держит ту же таблицу и краснеет,
если константу «поправят».

⚠️ Запускать с диска **C:** — на `I:` действует AppLocker (см. CLAUDE.md, правило 2).

## Что показала первая сборка (SDK 10.0.26100.0, x64)

Три места, где интуиция обманывает:

1. `FWP_V6_ADDR_AND_MASK` — **17 байт, выравнивание 1** (упакованная), а не 24.
2. `GUID` выровнен по **4**, не по 8; внутри `FWPM_ACTION0` лежит по смещению 4. Описать его
   полем `Uint64` нельзя — Dart выровнял бы структуру по 8.
3. `FWPM_FILTER_FLAG_PERSISTENT` и `FWPM_SESSION_FLAG_DYNAMIC` **оба равны `0x1`**.

Раскладку публичных структур WFP пересматривать при обновлении SDK не нужно: она заморожена
суффиксом `0` в имени типа (`FWPM_FILTER0`), новая версия приходит новым типом.
