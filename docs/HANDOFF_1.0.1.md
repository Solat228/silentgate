## 1. ГЛАВНОЕ: `noRealIp` больше не перекрывает явные правила пользователя

### Симптом, с которого начали
Пользователь: «Приложение chrome.exe — Туннель, но **все** сайты идут через туннель. То есть при
выбранном приложении я не могу рулить сайтами отдельно? Сайт example.org должен идти прямо».

### Куда НЕ надо смотреть (проверено, там всё правильно)
Порядок правил в конфиге **корректен**. Правило сайта стоит ВЫШЕ правила приложения во всех трёх
режимах `SplitMode`. Сгенерированный `route.rules`:

```
[0] {"action":"sniff"}
[1] {"protocol":"dns","action":"hijack-dns"}
[2] {"ip_cidr":["<IP сервера>/32"],"action":"route","outbound":"direct"}
[3] {"process_name":["xray.exe","sing-box.exe","silentgate.exe"],"action":"route","outbound":"direct"}
[4] {"ip_is_private":true,"action":"route","outbound":"direct"}
[5] {"domain_suffix":["example.org"],"action":"route","outbound":"direct"}     ← сайт
[6] {"domain_suffix":["example.net"],"action":"route","outbound":"proxy"}
[7] {"process_name":["chrome.exe"],"action":"route","outbound":"proxy"}   ← приложение НИЖЕ
```

Два независимых агента и я сам это воспроизвели. **Не тратить время на перестановку правил.**

### Настоящая причина
`singbox_config_builder.dart`, строка была:

```dart
final directOut = options.noRealIp ? 'proxy' : 'direct';
_addSiteRule(rules, split, AppAction.direct, directOut);   // «Прямо» → proxy
```

То есть настройка «Не выходить под реальным IP» по замыслу переписывала в «через VPN`
**КАЖДОЕ** пользовательское правило «Прямо» — и сайты, и приложения. Правило `example.org` уезжало
в `"outbound":"proxy"`, а интерфейс продолжал показывать чип «Прямо» и рисовать прямую ветку
в `RouteDiagram`. Обратной связи не было вообще.

**Как подтвердилось:** посмотрел фактический файл настроек (`silentgate_settings.json`) —
там оказалось `"noRealIp": true` при `"killSwitch": true` и несколько правил сайтов с
`"action": "direct"`. Затем сгенерировал конфиг с `noRealIp: true` и увидел, что правило
«Прямо» уехало в `{"domain_suffix":[…],"outbound":"proxy"}`.

> Здесь и далее домены в примерах — нейтральные заглушки (`example.com`/`example.org`/…):
> реальные правила маршрутизации пользователя в репозиторий не выносим.

> ⚠️ **Методический урок.** Один из проверяющих агентов ОПРОВЕРГ эту (верную) гипотезу с
> формулировкой «предпосылка `noRealIp == true` не доказана, это не дефолт». Доказательством
> оказался файл настроек пользователя, которого у агента не было. **Смотреть фактические
> настройки пользователя раньше, чем строить теории.**

### Что сделано (решение согласовано с пользователем)
Пользователь выбрал: **явные правила сайтов главнее** + **галочка в самом правиле**.

- У `AppRule` и `SiteRule` (`core/settings/split_tunnel.dart`) появилось поле
  **`allowRealIp`, умолчание `true`**. Старые правила из JSON получают `true`
  (`j['allowRealIp'] as bool? ?? true`) — **чинятся сами, миграция не нужна**.
- `_addAppRules` разводит «Прямо» на две группы:

```dart
_addSiteRule(rules, split, AppAction.direct, 'direct', allowRealIp: true);
_addSiteRule(rules, split, AppAction.tunnel, 'proxy');
_addActionRule(rules, split, AppAction.direct, 'direct', allowRealIp: true);
_addActionRule(rules, split, AppAction.tunnel, 'proxy');
if (options.noRealIp) {
  _addSiteRule(rules, split, AppAction.direct, 'proxy', allowRealIp: false);
  _addActionRule(rules, split, AppAction.direct, 'proxy', allowRealIp: false);
}
```

Фильтрация по `allowRealIp` применяется **только при `options.noRealIp`** — при выключенной
настройке «Прямо» и так прямое, флаг ни на что не влияет.
- UI (`ui/split_tunnel_screen.dart`): переключатель «Разрешить реальный IP» в `_RuleDialog`
  (виден только у действия «Прямо» и только при включённом `noRealIp`), в списке — подпись
  `⚠ реальный IP` / `🛡 через VPN` (метод `_ruleSubtitle`).
- `_setSitePort` переписан на `copyWith`: раньше пересобирал `SiteRule` конструктором и **терял бы**
  новый флаг при каждой правке порта.

### Побочно исправлено
`noRealIp` **залипал**: переключатель рисуется только при `killSwitch`, но при выключении
kill switch / autoReconnect сам флаг не гасился — оставался включённым, продолжал действовать и
при этом ИСЧЕЗАЛ из настроек, снять его было нечем. Теперь гаснет вместе с ними
(`settings_screen.dart`, оба обработчика).

## 2. Утечка DNS: `dns.rules` теперь зеркалит маршруты

Нашлось попутно, но это **самостоятельный дефект**, а не следствие первого.

Было единственное DNS-правило `{'outbound': ['direct'], 'server': 'dns-local'}` и
`final: dns-proxy`. В TUN-режиме это правило **не срабатывает никогда**: назначение соединения из
TUN — всегда IP, а не имя, поэтому `outbound`-матчинг для DNS-запроса не наступает. Имя роутер
узнаёт только из сниффинга. Итог: **весь** DNS уходил в `dns-proxy` (через туннель), включая домены,
помеченные «Прямо» — запрос всё равно раскрывался провайдеру туннеля, а CDN отдавал адрес в стране
выхода.

Добавлен `_dnsSiteRules`; порядок в `dns.rules`:
1. `block` → `{'domain_suffix': [...], 'action': 'reject'}` (выше всех — заблокированный домен
   не должен даже резолвиться);
2. «Прямо» + `allowRealIp` → `dns-local`;
3. «Туннель» → `dns-proxy`;
4. при `noRealIp` — «Прямо» без галочки → `dns-proxy` (иначе прямой резолв выдал бы реальную
   геолокацию ещё до соединения);
5. старое `{'outbound':['direct'],'server':'dns-local'}` оставлено последним, но **считать его
   рабочим сплитом нельзя**.

> ⚠️ Осознанный размен, который стоит держать в голове: домен «Прямо» теперь резолвится ЛОКАЛЬНО.
> В сети с отравленным DNS это может дать подложный ответ там, где раньше приходил чистый ответ
> из-за туннеля. Сейчас это считается правильным (прямое правило должно быть прямым целиком),
> но если появятся жалобы — вот где искать.

**Валидация:** `test/repro_split_site_test.dart` выгружает 6 конфигов
(3 режима × noRealIp вкл/выкл) в `app/build/split-configs/`, все приняты настоящим
`engine/windows/bin/sing-box.exe check -c` с кодом 0.

## 3. Автопереподключение сжигало все 8 попыток в одну миллисекунду

Всплыло при разборе жалобы «hysteria2 на винде не работает». В `app.log` пользователя:

```
12:55:01.256419 [WARN] Автопереподключение: обрыв → попытка 2 через 3 с
12:55:01.256419 [WARN] Автопереподключение: обрыв → попытка 3 через 8 с
12:55:01.257917 [WARN] Автопереподключение: обрыв → попытка 8 через 20 с
12:55:01.257917 [ERROR] Автопереподключение: исчерпаны попытки (8)
```

Восемь попыток с задержками до 20 с — **в одну миллисекунду**. Плюс параллельные цепочки
(три «попытка 1» на `.239`, `.252`, `.256`).

**Причина:** `scheduleRetry` не был защищён от повторного входа. Один обрыв приходит несколькими
событиями — при hysteria2 в TUN-режиме одновременно умирают процесс туннеля и процесс прокси-ядра,
у каждого свой `onCoreDied`, сверху может прилететь `onNetworkChanged`. Каждое событие
инкрементировало `_attempt` и перепланировало таймер (отменяя предыдущий), так что реально
выполнялась только последняя попытка, а лимит был уже выжжен.

**Фикс** (`engine/engine_base.dart`, в начале `scheduleRetry`):

```dart
if (_retryTimer?.isActive ?? false) return true;
```

Пока запланированная попытка не отработала, новые события считаются тем же обрывом.

Для тестов добавлены `@visibleForTesting` `attemptsUsed` и `dropPendingRetry()` — иначе тест ждал бы
реальный backoff. **Старый тест `попытки исчерпываются на maxAttempts` закреплял именно сломанное
поведение** (8 мгновенных вызовов = 8 попыток) и был переписан.

> ⚠️⚠️ **ВАЖНАЯ ПОПРАВКА — я ошибся в доказательстве.** Строки выше пришли НЕ из работы приложения,
> а из моих же прогонов `flutter test`: `AppLog` писал в боевой `%APPDATA%\SilentGate\app.log`,
> а тестовый движок гонял `scheduleRetry` в тесном цикле. Улика — соседняя строка
> «Переключаюсь на запасной сервер: **b**»: `b` это фикстура `_server('b')` из
> `engine_base_test.dart` (32 вхождения). Запись под `FLUTTER_TEST` теперь отключена.
>
> Что из этого следует:
> * дефект отсутствия защиты от повторного входа **реален** — подтверждён чтением кода и
>   регресс-тестами, страж нужен;
> * но **в продакшене он не наблюдался**, и **причина отказа hysteria2 остаётся неизвестной**.
>
> Конфиг hysteria2 пользователя при этом **валиден** (`sing-box check` = 0, тип hysteria2,
> TLS + alpn h3, порт 443). Следующему агенту: искать причину заново. Сильная непроверенная
> гипотеза из штурма — `hijack-dns` стоит ВЫШЕ loop-protection, и прокси-ядро резолвит адрес
> своего же сервера через самого себя. Отдельная проблема: **у прокси-ядра нет файла лога**,
> поэтому причину отказа физически негде посмотреть — это чинить первым.

## 4. Порядок плейсхолдеров l10n — класс багов, который не ловит компилятор

Симптом: трафик подписки показывался как «1100.0 GB of 6.1 GB» (израсходовано и лимит наоборот).

**Причина не в переводе и не в парсере.** Заголовок `subscription-userinfo` разбирался верно
(`upload=0; download=6610490559; total=1181116006400`), вызов написан верно
(`l.subBarUsage(used, total)`). Но у ключа не было `@subBarUsage`, а **без метаданных `gen_l10n`
сортирует параметры сгенерированного метода ПО АЛФАВИТУ**:

```dart
String subBarUsage(Object total, Object used);   // было: (total, used) — алфавит
String subBarUsage(String used, String total);   // стало: как в строке
```

Вызов передавал `(used, total)` → значения молча менялись местами. Типы совпадают, компилятор молчит.

Поражены были три ключа: `subBarUsage`, `homeAutoConfigProgress`, `jsonProfileServers`. Порядок
объявлен явно **у всех** строк с 2+ подстановками (13 ключей). Тест
`порядок плейсхолдеров объявлен и совпадает с порядком в строке` в `test/l10n_test.dart` это стережёт.

Проверено вживую в эмуляторе: теперь `6.1 GB of 1100.0 GB`.

> ⚠️⚠️ **ВАЖНО, НЕ ПОВТОРИТЬ МОЮ ОШИБКУ.** Я сначала «починил» турецкие и китайские переводы,
> которые ставят плейсхолдеры в другом порядке, — и был **неправ**, откатил. Строка
> `{total} hizmetten {ok} tanesi` = «из {total} сервисов {ok}» — это **правильный турецкий**.
> Именованные плейсхолдеры на то и именованные, чтобы язык расставлял их по своей грамматике.
> Ломает значения не перевод, а порядок ОБЪЯВЛЕНИЯ, общий для всех локалей.
> Тест, требующий одинакового порядка в переводах, — вредный, я такой написал и удалил.
> Единственная правка перевода, которая осталась: `tr` `subBarUsage` `{total} / {used}` →
> `{used} / {total}` — там голый формат «A / B» без слов, грамматика разворот не оправдывает.

## 5. Новое в интерфейсе

**Индикатор «VPN активен»** — `ui/widgets/vpn_active_badge.dart`. Живёт в `MaterialApp.builder`,
поэтому работает на **всех** экранах, включая те, что появятся позже, — не нужно вставлять в каждый
`Scaffold`. `NavDepthObserver` (в `navigatorObservers`) считает глубину стека: плашка показывается
только поверх **вложенных** экранов (на главном состояние и так видно по кнопке Connect).
Обёрнута в `IgnorePointer` — нажатия не перехватывает никогда.

**Выделяемый текст** — `ui/widgets/sel_text.dart` (`SelectableText` +
`AdaptiveTextSelectionToolbar`, в стиле уже существующего `InfoTooltip`). Применён к заголовкам
разделов и абзацам-пояснениям. Адрес сайта и путь к программе теперь выделяются и копируются
кнопкой в диалоге правила.

> ⚠️ Два ограничения, выясненные при инвентаризации, — **не нарушать**:
> 1. **НЕ оборачивать приложение в `SelectionArea`.** Она перехватывает правый клик (а на нём
>    держатся контекстные меню серверов и подписки — 5 из 7 действий) и долгое нажатие, которое
>    на Android означает то же меню; плюс протяжка пальцем по списку начнёт выделять текст вместо
>    прокрутки, и каждый `RenderParagraph` регистрируется в `SelectionRegistrar` (список из 100+
>    серверов перестраивается на каждое обновление пинга).
> 2. **НЕ ставить `SelText` внутрь кликабельных строк** (`ListTile` с `onTap`, `SwitchListTile`,
>    `RadioListTile`): жест выделения выигрывает арену у `InkWell`, и строка перестаёт нажиматься.
>    Там — копирование отдельным действием.

**Проверка сервисов** — `ServiceCheckController.autoCheckAll`: **один** автоматический прогон при
подъёме туннеля, дальше только вручную. Повтор для той же эпохи запрещён (`_autoRanEpoch`), поэтому
перестроение интерфейса, возврат с другого экрана и смена темы прогон не запускают.
⚠️ Это **отменяет решение 0.13.0** «авто-проверок НЕТ» — по прямой просьбе пользователя.

**Отчёт поддержки (Windows)** теперь печатает `noRealIp` и сводку раздельного туннелирования.
Раньше Android-версия его печатала, а Windows — нет, из-за чего эта причина по отчёту
**физически не диагностировалась**.

## 6. Android (для полноты)

- Чёрный экран при импорте подписки: закрытие экрана снимало последний маршрут — теперь
  `if (nav.canPop()) nav.pop()`.

  крутит бесконечную анимацию, и это читалось как «подписка вечно обновляется». Добавлен
  `SubscriptionInfo.unlimitedTraffic` (Remnawave кодирует безлимит нулём, как и `expire=0`).
- `platform/PlatformChannels.kt` — нативные каналы устройства (HWID через `ANDROID_ID`,
  `Build.VERSION.RELEASE`, модель) и открытия ссылок. Без них вызовы падали с
  `MissingPluginException`, в отчёте стояли «unknown», а кнопки поддержки не делали ничего.
- APK пересобран и проверен в эмуляторе (Android 11 x86_64): подписка на 116 серверов
  импортируется, главный экран и настройки рисуются, трафик показывается верно.

## 6-bis. Adversarial-ревью самих правок 1.0.1 (4 линзы × проверка оппонентом)

После первого коммита правки прогнали через 11 агентов: 4 линзы ревью, каждая находка отдана
отдельному агенту с заданием ОПРОВЕРГНУТЬ. Из 15 находок 5 опровергнуты (завышенная критичность
либо неверная предпосылка), остальные подтверждены независимым репро. **Шесть подтверждённых
дефектов были в моём же новом коде — все закрыты**, тесты 264 → **287**.

| Дефект (мой) | Суть | Как закрыт |
|---|---|---|
| **Утечка реального IP** | Вторая группа правил «Прямо» (возвращённые под защиту) дописывалась в хвост — ПОСЛЕ правил приложений. Инвариант «все сайты выше всех приложений» (#3.5) держался только для половины сайтов. `Telegram.exe` = «Прямо» перекрывал `bank.ru` с СНЯТОЙ галочкой → трафик уходил под реальным IP, а UI рисовал этой строке щит «под защитой» | `_addAppRules` пересобран: все три группы сайтов → потом все три группы приложений. Проверено на сгенерированном конфиге: `bank.ru→proxy` (8) выше `Telegram.exe→direct` (10) |
| **Плашка VPN пропадала навсегда** | `navigatorObservers: [NavDepthObserver()]` создавал нового наблюдателя на КАЖДУЮ пересборку `MaterialApp` (смена темы/языка) — счётчик глубины уходил в минус | Единственный экземпляр `NavDepthObserver.instance` + кламп на 0 |
| **Плашка вылезала поверх диалога** | Диалоги и всплывающие меню — тоже маршруты, счётчик их считал | Фильтр `route is PageRoute` |
| **Исключение на каждом «Отключить»** | `ServiceChecksRow.dispose()` звал `context.read` — дерево уже разбирается, провайдер не находится, сброс результатов не отрабатывал | Контроллер запоминается в `didChangeDependencies` |
| **Страж ретрая неатомарен** | Проверка стояла перед `await teardownCore`; на этом await второе событие успевало проскочить до создания таймера | Синхронный флаг `_retryPending`, ставится до первого await |
| **Вечное «Подключение…»** | Исключение внутри колбэка таймера ловить некому: единственная запланированная попытка умирала молча | `_runAttempt()` с перехватом → следующая попытка либо статус ошибки |
| **Гонка с «Отключить»** | `teardownCore` идёт до 3 с; нажатое в это окно «Отключить» затиралось — `scheduleRetry` возвращал статус в «Подключение…» и ставил таймер уже ПОСЛЕ отключения | Проверка `_userStopped` после каждого `await teardownCore` |
| **DNS-блок убивал весь домен** | Правило «блок `example.com:8443`» зеркалилось в DNS без порта → не резолвился ВЕСЬ домен, хотя маршрут блокирует один порт | Правила с портом в DNS-зеркало не попадают (маршрут остаётся точным); пустые домены отфильтровываются |

### Подтверждённые находки, которые я НЕ чинил (для следующего захода)

- **`SplitMode.all` + `noRealIp`** (high): правила применяются в конфиге, но UI их прячет и обещает
  «всё через VPN». Теперь, когда «Прямо» снова означает «прямо», скрытые правила выпускают трафик
  и DNS наружу. Нужно решение: либо не применять правила при `mode == all`, либо перестать их прятать.
- **Миграция снимает защиту** (medium): у всех старых правил `allowRealIp` молча = `true`. Для
  пользователя с `noRealIp` это осознанное следствие выбранного поведения («явные правила главнее»),
  но стоит показать разовое уведомление.
- **Android, паритет** (medium): правила приложений пишутся как `process_name`/`process_path_regex`,
  которых на Android нет — «Блок» не блокирует; при `SplitMode.onlySelected` одновременно отдаются
  `include_package` и `exclude_package`, чего `VpnService.Builder` не принимает.
- **Android, сервис-чипы** (medium): на обычном VLESS-сервере локального http-прокси нет, поэтому
  новый автопрогон красит все три сервиса красным. Нужно либо не показывать ряд, либо поднимать
  inbound.
- **`dns-local` на Windows с поднятым TUN** (high, требует живой проверки): «системный резолвер»
  может указывать на сам туннель — тогда правило «Прямо» резолвится через VPN, чего и добивались
  избежать. Проверять живьём.
- **Windows: `_attempt` в наследнике мёртв** после выноса базы — номер попытки в статусе не растёт.

### Профилактика класса «интерфейс показывает не то, что происходит»
Три бага 1.0.1 объединяет одно: артефакт, который **реально** управляет поведением (массив
`route.rules`, сигнатура сгенерированного l10n-метода, фактические моменты срабатывания таймера),
разошёлся с моделью в голове интерфейса — и нигде эти двое не сверялись. Предложения по убыванию
ценности:
1. **`core/routing/route_explain.dart`** — чистая функция «конфиг + запрос → выигравшее правило»,
   повторяющая семантику sing-box «первое совпадение». Тогда инварианты утверждаются на ФАКТИЧЕСКОМ
   конфиге, а не на предположениях. Сегодняшняя утечка была бы поймана одним ассертом.
2. **`effectiveRoute(rule, settings)`** — единый источник истины для конфига И интерфейса. Сейчас
   «куда пойдёт трафик» вычисляется дважды и независимо (`_addAppRules` и `_ruleSubtitle`), что и
   позволило чипу врать.
3. **CI**: `flutter analyze` и `flutter test` сейчас **не запускаются нигде**. Плюс проверка дрейфа
   `lib/l10n/gen` и сверка сигнатур с объявленным порядком плейсхолдеров.
4. **Отчёт поддержки**: печатать ФАКТИЧЕСКИЕ правила маршрутизации и DNS, а не пересказ настроек;
   хронологию переподключений с колонкой Δ; блок `[Предупреждения]` с самопроверками в начале.
5. Экран «Почему трафик пошёл именно так» — объяснение маршрута по реальному конфигу.

### Android — что реально не работает (для планирования)
- Правила **приложений** не работают вовсе: пишутся `process_name`/`process_path_regex`, которых на
  Android нет. «Блок» тихо разрешает трафик.
- Галочка `allowRealIp` из 1.0.1 не доехала до слоя ОС.
- Гео-базы не поставляются — панельные профили «Авто» не запустят Xray.
- Kill switch включается, но ничего не делает.
- Решение 4а (кэшированный `FlutterEngine`) не реализовано — интерфейс и туннель расходятся.
- Счётчики трафика — нули. Статусы движка остаются русскими во всех 10 языках.

### Прочее по Windows
- `tool/emit_*.dart` чинится **удалением одного импорта** (~5 строк работы).
