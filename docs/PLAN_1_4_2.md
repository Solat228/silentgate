## 0. Находка, которой не было в жалобе: потеряно 273 результата пинга из 374

Владелец сообщил про баннер обновления подписки: у сервера «Москва 1. GRPC» каждый раз пишется
`+1 · −1`, хотя серверы не меняются. Разбор на его живых данных (локально, без сети) показал, что
баннер — симптом, а болезнь тяжелее.

| Что | Сколько |
|---|---|
| Результатов пинга сохранено | **374** |
| Серверов в подписке сейчас | **101** |
| Ключей, которых больше нет | **273**, из них **190 — gRPC** |

**Причина.** Ключ сервера — это его share-ссылка (`VpnServer.key => rawLink`), и по ней же лежат
пины, ручные правки и результаты пинга. Один и тот же gRPC-сервер существует в ДВУХ написаниях:

* мёртвые ключи: `…&serviceName=…&mode=…`
* живые ключи: `…&path=…` (без `mode`)

Разбор ссылки читает ОБА имени параметра (`share_link_parser.dart:65`:
`path: _nz(q['path'] ?? q['serviceName'])`), а сборка пишет ТОЛЬКО `path`
(`vpn_server.dart:buildShareLink`). Значит ссылка, пришедшая в текстовом формате подписки, после
разбора и обратной сборки становится ДРУГОЙ СТРОКОЙ при том же сервере. Панель Remnawave выбирает
формат ответа по `User-Agent`, поэтому на каждом переключении формата (или правке Response Rules)
все gRPC-серверы выглядят исчезнувшими и появившимися заново.

⚠️ **Класс дефекта:** идентичность объекта вычисляется НЕ КАНОНИЧЕСКИ — два законных представления
одних и тех же данных дают разные ключи. Тот же класс, что и `AppRule.matchKey` в 1.4.1 (ключ
тождественности не совпадал с ключом сопоставления). Здесь цена выше: молча теряются данные
пользователя.

## Задачи

### Задача 1. Канонический ключ сервера + миграция

**Решение владельца:** сперва найти причину, потом чинить (причина найдена, см. §0).

1. `VpnServer.buildShareLink()` становится ЕДИНСТВЕННЫМ источником ключа: любая входящая ссылка
   проходит разбор → сборку, поэтому оба формата дают одну строку.
   ⚠️ Проверить идемпотентность на всех протоколах: `parse(build(parse(link))) == parse(link)`.
2. **Разовая миграция** сохранённых данных: пины, override'ы и результаты пинга переносятся со
   старых ключей на канонические. Ключ, который не разбирается, оставляем как есть — выбрасывать
   чужие данные нельзя.
3. Диф подписки дополнительно сравнивает по «протокол + адрес + порт + имя», чтобы баннер не врал
   даже при будущих расхождениях формата.
4. Диагностика в журнал: «ключ сменился: <было> → <стало>» — чтобы следующее расхождение было
   видно сразу, а не через полгода по потерянным пингам.

⚠️ Тест обязан ловить ИМЕННО это: ссылка с `serviceName=` и ссылка с `path=`, описывающие один
сервер, дают ОДИН ключ; миграция переносит пинг со старого ключа на новый.

### Задача 2. API — отдельный экран

**Решение владельца:** отдельный экран из настроек (как URL-схемы).

`_ApiSection` уезжает в `ui/api_screen.dart`; в настройках остаётся строка со стрелкой.

### Задача 3. Читаемость настроек на Windows — четыре меры

**Решение владельца:** делать все четыре; боковое меню — тестово, «посмотрю как выглядит».

1. **Ширина ограничена и центрирована** (~760 px). Сейчас ограничения нет вовсе, поэтому на широком
   окне тумблер уезжает к правому краю, а строка тянется через весь экран.
2. **Боковое меню разделов** на широком окне (список слева, содержимое справа). На узком окне и на
   телефоне раскладка прежняя — иначе разойдёмся с мобильной вёрсткой.
3. **Сворачиваемые разделы**, состояние ЗАПОМИНАЕТСЯ. ⚠️ По умолчанию всё развёрнуто — прямое
   указание владельца.
4. **Поиск по настройкам** в шапке: решает исходную жалобу «как искать версию непонятно».

### Задача 4. Скорость сервера — умно

**Решение владельца:** «1 и 2 варианты, НО умное. Сначала выполняется GET-пинг, и если сервер его
НЕ проходит, то и скорость проверять не нужно. У таких серверов вместо значений скорости показывай
минусы или крестики с пояснением при наведении».

1. Отдельное действие «Измерить скорость» для ОДНОГО сервера.
2. Кнопка прогона по всему списку — с предупреждением об объёме трафика и подтверждением.
   ⚠️ 101 сервер × 5–20 МБ = 0,5–2 ГБ подписки за прогон, поэтому подтверждение обязательно.
3. **Гейт по проверке канала:** меряем скорость только у серверов с `PingVerification.passed`.
   Не прошёл — прочерк с пояснением, а не пустое место и не ноль.
4. Скорость, уже замеренная автонастройкой, показывается сразу и повторно не меряется.

### Задача 5. Строка сервера

**Решение владельца:** пинг и скорость столбиком у края.

* есть скорость — пинг сверху, скорость под ним;
* нет скорости — пинг по центру строки;
* не прошёл GET — на месте скорости прочерк с подсказкой;
* кнопка правки уезжает вплотную к шеврону.

### Задача 6. Новая настройка «Обновлять подписку при запуске приложения»

**Решение владельца:** новая настройка, включена по умолчанию. Сейчас подписка обновляется только
по таймеру (12 ч) и вручную.

⚠️ Настройка обязана переживать перезапуск (страж `settings_roundtrip_test` перебирает все ключи).
⚠️ В `reconnectReasons` НЕ добавлять: обновление подписки не требует переподключения.

### Задача 7. Пинг всех подписок и счётчик у подписки

**Решение владельца:** обычная кнопка — текущая подписка, пункт меню — все подписки. Рабочий =
прошёл проверку канала. Счётчик показывать всегда.

1. Пункт «Пинг серверов» в меню переключателя гоняет серверы ВСЕХ подписок (у владельца 124).
2. У каждой подписки в меню — «всего · рабочих». До первого пинга рабочих не показываем.
3. Пояснение по наведению: что значит каждое число.

⚠️ Серверы неактивных подписок лежат в профилях ссылками — их надо восстановить так же, как это
делает переключение подписки, иначе пинг пойдёт по пустому списку.
