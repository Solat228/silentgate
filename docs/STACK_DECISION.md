# Выбор стека — обоснование

Документ фиксирует, **на чём** и **почему** пишется SilentGate. Решения основаны на разборе
реальных клиентов (включая teardown APK Happ и десктопных бинарников) — см.
[research/RESEARCH_SUMMARY.md](research/RESEARCH_SUMMARY.md).

---

## 1. Итоговое решение

| Что | Выбор |
|---|---|
| **UI (все платформы)** | Flutter / Dart — единый код |
| **Движок (ядро)** | Xray-core (Go) |
| **Привязка ядра — desktop** | `xray` отдельным процессом (subprocess) |
| **Привязка ядра — Android** | самосборный gomobile AAR из `libXray` (MIT), in-process в `VpnService` |
| **Привязка ядра — iOS** | `libXray.xcframework` в нативном Swift `NEPacketTunnelProvider` |
| **Захват трафика — Windows MVP** | системный прокси (WinINET) без TUN |
| **Захват трафика — позже** | TUN: `wintun` + `hev-socks5-tunnel` (MIT) через привилегированный хелпер |
| **Бэкенд/авторизация/оплата** | Python (существующие боты) + Remnawave API |

## 2. Почему Flutter, а не другое

Как «сделаны» популярные клиенты (проверено):

- **Happ** — Android: нативный **Kotlin**; Desktop: **C++ Qt6/QML**; iOS: нативный (Swift). Закрытый код.
- **v2RayTun** — Android: **Kotlin**; iOS/macOS: **Swift**; **Windows/Linux: Flutter/Dart**. Закрытый код.
- **v2rayNG / NekoBox** — Android, **Kotlin**, открытый код **GPL-3.0** (копировать нельзя).
- **Hiddify** — **Flutter/Dart** на всех платформах + нативный Swift-extension на iOS. Открытый.

Вывод: у команд с ресурсами — нативный код под каждую ОС (Kotlin+Swift+Qt). Для **соло-разработчика**
это три экосистемы и три UI — главная причина заброшенных одиночных клиентов.

**Flutter выбран потому что:**
1. **Один язык (Dart) на 5 платформ.** Наименьшая инвестиция для покрытия всего.
2. **Прямые прецеденты в этой нише:** v2RayTun (Windows) на Flutter, Hiddify (всё, включая iOS с нативным NE) на Flutter.
3. **Dart легко даётся** тому, кто знает Python+JS (C-подобный синтаксис, async/await, null-safety).
4. **Desktop-архитектура «UI ↔ subprocess»** делает язык UI почти не важным для движка — но код подписок,
   моделей и экранов переиспользуется на мобильных.

**Отвергнутые варианты:**
- **Kotlin + Swift + Qt (нативно)** — лучший UX и минимальный размер, но 3 языка. Только с командой.
- **Kotlin Multiplatform / Compose MP** — один язык, но iOS/desktop менее зрелые; нет прецедентов среди VPN-клиентов.
- **React Native** — использует ваш JS, но слабый Windows/Linux; ни один изученный клиент не на RN.
- **Python (PyQt, как Furious)** — ваш сильный язык, но **не идёт на Android/iOS** → desktop-only тупик.
- **Electron / Tauri** — desktop-only; Tauri требует Rust.

## 3. Почему Xray-core, а не sing-box

| | Xray-core | sing-box | mihomo |
|---|---|---|---|
| Язык | Go | Go | Go |
| VLESS + Reality + XTLS-Vision | ✅ референс | ✅ | ✅ |
| Hysteria2 | ✅ (с v26.1.23) | ✅ | ✅ |
| TUIC | ❌ | ✅ | ✅ |
| Память на мобиле | ~80–120 МБ | ~40 МБ | — |
| **Лицензия** | **MPL-2.0** | **GPL-3.0 + no-name** | **GPL-3.0** |
| Годится для закрытого приложения (линковкой) | ✅ | ❌ | ❌ |
| Доминирует в RU-панелях (Remnawave/Marzban/3x-ui) | ✅ | — | — |

**Xray-core** выбран потому что:
- Ваша панель **Remnawave** и подписки — это VLESS/Reality, где Xray — референс.
- **MPL-2.0** — копилефт на уровне файлов: можно статически линковать в **закрытое коммерческое**
  приложение; открывать нужно только изменённые файлы самого ядра (если вы их правите).
- Прецеденты: Happ, v2RayTun, Streisand — все закрытые, все встраивают Xray-core.

**sing-box/mihomo (GPL)** — линковка (в т.ч. gomobile/libbox) делает всё приложение производным GPL →
закрытый код невозможен. Допустимо только **отдельным процессом** (как Happ использует sing-box для TUN
на десктопе). Внутри iOS NE extension ядро обязано линковаться → sing-box там для закрытого кода закрыт.

Компромисс по памяти на iOS решается: обрезка geo-файлов, `libXray` форсит GC раз в секунду, `GOMEMLIMIT`,
отключение статистики. Если Xray не влезет в лимит NE — это главный риск (см. IOS.md).

## 4. Лицензии — что можно и нельзя <a name="лицензии"></a>

**Можно встраивать в закрытый SilentGate:**
- **Xray-core — MPL-2.0.** Линковать можно; открывать — только модификации MPL-файлов ядра + указать источник.
- **XTLS/libXray — MIT.** Идеальная обёртка ядра (один JSON-вход `Invoke`) для Android/iOS/macOS.
- **hev-socks5-tunnel — MIT.** C-tun2socks для TUN-режима.

**Условно:**
- **AndroidLibXrayLite — LGPL-3.0.** gomobile AAR ≈ статическая линковка → обязательства LGPLv3 §4
  (дать возможность релинковки). Обёртка — это ~3 небольших Go-файла → **пишем свою** MIT/MPL-чистую поверх libXray.

**Нельзя:**
- **sing-box / mihomo — GPL-3.0**: линковать в закрытый код нельзя (только отдельным процессом).
- **Код v2rayNG / NekoBox / husi / Hiddify** — GPL: только **архитектурный референс**, копировать нельзя.
- **Happ / v2RayTun / Streisand** — закрытые, переиспользовать нечего. ToS Happ запрещает ребрендинг.

**Итог:** легально-чистый закрытый стек = **Xray-core (MPL) + libXray (MIT) + hev-socks5-tunnel (MIT) + свой UI-код**.
GPL-компоненты (если понадобятся) — только отдельными desktop-процессами.

## 5. Порядок разработки платформ

Пользователь начинает с **Windows** (по запросу). Полный рекомендованный порядок и причины —
в [ROADMAP.md](ROADMAP.md). Кратко:

1. **Windows** (сейчас) — тривиальная subprocess-модель, быстрый видимый результат.
2. **Android** — крупнейшая RU-аудитория, нет цензуры магазина (APK через бота/GitHub).
3. **iOS** — самый сложный: аккаунт Organization, NE, лимит памяти, риски RU App Store.
4. **macOS / Linux** — переиспользуют desktop-код.

До выхода мобильных версий iOS/Android-пользователей можно временно направлять на **стоковый Happ**
с вашей ссылкой Remnawave (у Remnawave first-class интеграция с Happ) — это ничего не стоит.
