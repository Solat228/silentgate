### Чужой опыт: Clash Verge Rev (разбор 02.08.2026)

Десктопный клиент на Tauri + Rust, ядро mihomo отдельным процессом. Читали код и issue —
интересны не решения, а **грабли**: половина их бед уже случалась у нас, и это подтверждает
принятые решения; вторая половина — то, на что мы ещё наступим.

**Взять к себе:**
- [ ] **Windows Job Object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`** на дочерние ядра. ОС сама гасит
      sing-box/Xray при смерти GUI — без реестра осиротевших PID и без подбора по пути, которым мы
      сейчас занимаемся (`CoreCleanup`). Если создать job не удалось, они немедленно убивают
      ребёнка, а не запускают его «на удачу». Это строго надёжнее нашего подхода.
      Смотреть: `src-tauri/src/core/manager/state.rs`.
- [ ] **Категоризация ошибок конфига.** Они запускают ядро с `-t` (у нас `sing-box check`) и
      разбирают stderr на классы: синтаксис YAML, отвергнуто ядром, процесс умер. Пользователь
      получает внятный тост вместо простыни. Дёшево поверх того, что у нас уже есть.
- [ ] **⚠️ Переприменять DNS и маршруты после выхода из сна.** Их issue #7593: после resume
      системный DNS в TUN-режиме не переприменяется → **утечка DNS**. У нас `NetworkWatcher` следит
      за сменой сети, но пробуждение — отдельное событие, и я не уверен, что оно покрыто. Проверить.

**Подтвердило наши решения (ничего не делать, просто знать):**
- Автозапуск через `schtasks /Create /XML` — они делают так же, ДВЕ взаимоисключающие задачи
  (обычная и админская). Нюанс, которого у нас нет: XML пишется в **UTF-16LE с BOM**.
- Их issue #7403 — каскад окон UAC при перезапуске ядра. Ровно наш баг 1.0.2.
- Их issue #7521 — битый служебный state-файл (нули) кладёт приложение без права на восстановление.
  Наш аналог — BOM в `silentgate_settings.json`, уже вылечен. Вывод общий: **любой служебный файл
  обязан иметь путь самолечения**.
- Их issue #7511 — стек TUN `mixed` ломает UDP:443 на Windows. Зеркало нашего опыта на Android, где
  `system`/`mixed` не форвардили TCP. Вывод: **выбор стека нельзя отдавать пользователю вслепую**.
- Их issue #6741 — гонка «убили ядро асинхронно → новое не заняло порт», при этом системный прокси
  уже указывает на мёртвый листенер = «подключено, интернета нет». У нас это закрыто `_generation`
  и последовательным teardown.
- Их issue #7348 — счётчики считают и прямой трафик, тумблера «только проксированный» нет. **Ровно
  наша находка по Android.** Значит болезнь отраслевая, а не наша ошибка.
- **Kill switch у них отсутствует вовсе** (#6198 открыт с января 2026). После сегодняшней переделки
  наш заметно впереди.

**Отвергнуто осознанно:**
- Управляющий API ядра по named pipe вместо TCP (снимает вопрос секрета, CORS и занятого порта) —
  красиво, но их же issue #6287: пайп, созданный под одним уровнем целостности, не виден процессу с
  другим, и TUN ломается, если приложение запущено от админа. Наш `clash_api` на петле с
  обязательным секретом проще и предсказуемее.

### Xray-core: что изменилось и что проверить (исследование 02.08.2026)

Ядро перешло на календарные версии (актуальная **v26.7.28**), релизы раз в 2-4 недели и ВСЕ
помечены pre-release — это норма модели, а не предупреждение. Значит «версия ядра» в «О программе» —
дата, и сравнивать её как семвер нельзя.

**Проверено сразу, дефекта НЕТ:** параметр `encryption` проходит через нас насквозь — парсер читает
(`q['encryption'] ?? 'none'`), `buildShareLink` пишет обратно, Xray-фабрика кладёт в outbound. То
есть длинная строка VLESS Encryption (`mlkem768x25519plus.native.0rtt…`) переживёт round-trip и не
потеряет сервер. Это была главная опасность из отчёта — её нет.

**Исправлено сразу:** `allowInsecure` убран из tlsSettings (удалён из Xray в v26.2.6, автоотключение
с 01.06.2026). Значение было `false`, поведения не менял, но отправлять ядру удалённое поле — значит
однажды получить отказ конфига на обновлении и искать причину не там.

Осталось:
- [ ] **Проверить версию Xray, с которой собран наш `libXray`.** README libXray требует «только
      последний релиз Xray-core», а всё новое (PQ-поля, `password` вместо `publicKey`, `pcs`/`vcn`,
      новые отпечатки) появилось в 2026 году. Обновление libXray = обязательный регресс, не рутина:
      API нестабилен, единственная точка входа `Invoke(json)`, конверт ≤ 16 МиБ.
- [ ] **Расширить парсер share-ссылок** по актуальному стандарту (Discussion #716): `pqv`
      (mldsa65Verify), `pcs`, `vcn`, `ech`, `fm` (Finalmask), `mtu`/`tti` (mKCP), `type=xhttp` и
      `httpupgrade`. Панель отдаёт XRAY_JSON, но КЛЮЧ сервера у нас строится через `buildShareLink` —
      что ссылка не умеет нести, то теряется при round-trip, и сервер поднимется с урезанным
      набором признаков, то есть отличимым.
- [ ] **REALITY: `publicKey` переименован в `password`.** Писать новое имя, старое держать алиасом
      на чтение.
- [ ] **Отпечаток `fp` не запирать на `chrome`.** В v26.3.27 uTLS обновлён: Firefox, Safari и
      главное — X25519MLKEM768 в ClientHello. Настоящий Chrome шлёт гибридный PQ key share с 124-й
      версии; отпечаток без него в 2026 году выделяется.
- [ ] **`metrics`-инбаунд вместо процесса `xray api statsquery`.** Один HTTP GET на `/debug/vars`
      отдаёт трафик по inbound/outbound И результаты observatory (здоровье + задержка каждого узла
      профиля «Авто»). На Android процесс не запустить вовсе — это закрывает платформенное
      расхождение, которое у нас сейчас есть.
- [ ] Рассмотреть `convertShareLinksToXrayJson` из libXray как ЭТАЛОН для сверки нашего парсера в
      тестах (разбор новых параметров силами самого ядра), даже не переходя на него в проде.

**НЕ делать (проверено, преждевременно):**
- Hysteria2 забирать в Xray рано: #5911 — `clientManager` кэширует QUIC-соединение по адресу,
  игнорируя `auth` (несколько hy2-серверов на одном адресе схлопнутся в один), #5712 — Salamander.
  Критерий пересмотра — закрытие обоих. И TUIC в Xray не появится никогда по заявлению проекта, так
  что второе ядро в архитектуре остаётся в любом случае.
- Сносить sing-box из TUN-пути рано, хотя у Xray ТЕПЕРЬ ЕСТЬ свой TUN-inbound на том же `wintun.dll`,
  что у нас в поставке, и с `autoOutboundsInterface: "auto"` (встроенный аналог наших правил direct
  для своих процессов). Документация честно называет это «не L3-VPN, для сетевых профессионалов»,
  `dns` работает только на Windows, а ICMP-ответы генерируются локально — наш «пинг через туннель»
  начнёт врать. Прототип на Windows — да; снос выстраданного sing-box TUN — нет.
- Заменять нашу двухфазную проверку («TCP → GET/HEAD») на `burstObservatory`: при заблокированном
  REALITY-рукопожатии узел может считаться живым. Дополнять — да, заменять — нет.

**Мифы, которые в интернете живее всех живых** (важно, чтобы не «чинить» по советам с форумов):
`allowInsecure` — удалён; транспорт `tcp` давно переименован в **RAW**; WebSocket помечен legacy
(характерный ALPN `http/1.1`), замена — XHTTP; **SplitHTTP и XHTTP — это одно и то же**, старое имя;
JA3 мёртв с Chrome 108 (рандомизация порядка расширений), стандарт — **JA4**, который сортирует
перед хэшированием; «Xray с uTLS неотличим» — **нет**, issue #4900 закрыт как *not planned*: Go
канонизирует регистр заголовков и меняет их порядок, это ограничение Go, чинить не планируют.

### Подписки: что мы упускаем (исследование 02.08.2026)

Разбор стандарта и панели. Первоисточник — [XTLS Subscription Standards](https://github.com/XTLS/Xray-core/discussions/4877),
документация Remnawave (docs.rw) и v2RayTun (docs.v2raytun.com). Дёшево и заметно:

- [ ] **Читать `content-type`, а не угадывать формат.** Стандарт требует отдавать ему приоритет:
      `application/json` = XRAY_JSON, `text/plain` = base64. Сейчас формат определяется по UA и
      содержимому. Панель с 2.8.0 умеет «JSON subscription fallback clients» — может прислать не
      то, что мы ждём, и разбор поедет молча.
- [ ] **Читать HWID-ответы панели.** Без `x-hwid` подписка отдаёт **404**, а при упёршемся лимите
      устройств — `x-hwid-max-devices-reached`. Сейчас это выглядит как «подписка не пришла».
      Заголовки: `x-hwid-active`, `x-hwid-not-supported`, `x-hwid-max-devices-reached`,
      `x-hwid-limit`. Три строки кода превращают невнятную ошибку в «Достигнут лимит устройств».
- [ ] **Запоминать 301/308.** Стандарт требует обновить сохранённый URL подписки. Переедет панель
      на новый домен — пользователи отвалятся молча. У Hiddify для этого есть даже свой заголовок
      `moved-permanently-to`.
- [ ] **`profile-title` и `announce` могут приходить с префиксом `base64:`** — проверить, что
      разбираем. У Happ `announce` обрезается на 200 символах, v2RayTun кладёт в него цвет
      `#RRGGBB` — у нас такой код покажется мусором.
- [ ] **`profile-web-page-url`** (личный кабинет) — панель его настраивает (`SUB_WEBPAGE_URL`), мы
      не показываем. Естественная кнопка рядом с «Поддержка».
- [ ] **Принимать чужие deep-link при миграции:** `happ://add/<url>`, `clash://install-config?url=`,
      `sing-box://import-remote-profile/?url=`, `streisand://import/<url>`, `v2raytun://import/`,
      `hiddify://import/`. Стоимость почти нулевая, выигрыш при переходе с другого клиента заметный.
      ⚠️ `happ://crypt4/` и `crypt5/` расшифровать НЕЛЬЗЯ — ключи вшиты в само приложение Happ;
      надо честно так и написать, а не «неверный формат».
- [ ] **Своя схема в отраслевой форме:** у всех `<клиент>://add/<url>` или `://import/<url>`, у нас
      `silentgate://import?url=`. Принимать обе.
- [ ] **Попасть на страницу подписки как поддерживаемый клиент.** Гейткипера нет — владелец панели
      правит свой `app-config.json` (реестр примеров: `remnawave/templates`). Нужны deep-link
      указанной формы, SVG-иконка и строка в конфиге. Панель наша, значит делается за один заход.
- [ ] **Проверить парсер XRAY_JSON на новых протоколах панели:** 2.8.0 добавила Hysteria2, KCP,
      xhttp и ECH в генераторы конфигов; 2.7.0 отдаёт Hysteria2 ТОЛЬКО в Xray-Json.
- [ ] ⚠️ **Панель 3.0.0 (31.07.2026) переносила настройки подписки в заголовки ответа** и меняла
      структуру заголовков внешних squad'ов. Свериться перед обновлением панели.
- [ ] Сознательно НЕ поддерживаем заголовок `routing` (v2RayTun): он позволяет панели перекрыть
      пользовательские правила маршрутизации. После всего, что стоило раздельное туннелирование, —
      нет. Но знать о нём надо, чтобы не удивляться расхождению с другими клиентами.

### Долги по находкам ревью 01.08.2026

- [ ] **Нет стоящего теста на устаревший ответ подписки.** Фикс (`importSource` сверяет активную
      подписку до и после сетевого запроса) сделан и отревьюен, дефект воспроизводился агентом
      живьём на `MockClient`. Постоянного регресс-теста НЕТ: он требует изолированного `%APPDATA%`
      (`AppStorage`, `_subscriptionsStore` и соседи создаются внутри `AppState`), а писать из
      обычного прогона в боевой каталог пользователя нельзя. Варианты: сделать сторы внедряемыми
      либо завести тест с тегом `diag`, как у остальных, требующих изолированной папки.
- [ ] **Счётчик трафика на Android считает и прямой трафик.** `SingboxStats` берёт
      `uploadTotal`/`downloadTotal` того же ядра, что держит туннель, то есть ВСЕ соединения —
      включая уведённые правилом `package_name → direct`, `bypassLan` и локальный DNS. Windows
      считает только прокси-ядро, поэтому в той же конфигурации показал бы ноль. Рядом в
      интерфейсе стоит остаток трафика по подписке — цифры выглядят сопоставимыми, а меряют
      разное. Фикс: суммировать по `GET /connections` только соединения, чья цепочка не `direct`.
- [ ] **Экран автонастройки на Android виден и предлагает настройки, которых не будет.**
      `ProbeHarnessAndroid.supportsProxyRequests == false`, отказ (`AutoConfigUnsupported`)
      приходит только по факту нажатия «Начать». Дизейблить сразу, до кручения стратегии и бюджета.
- [ ] Версия ядра в «О программе» на Android — `н/д`; AAR в сборке уже есть, комментарий устарел.

### Защита от обнаружения VPN — ИССЛЕДОВАНО, см. `docs/research/VPN_DETECTION.md`

Главный вывод: **факт включённого VPN на Android скрыть нельзя.** Он отдаётся системой по
документированному API (`NetworkCapabilities.TRANSPORT_VPN`) без единого разрешения. Известная
попытка спрятать его (`okhsunrog/vpnhide`) требует root, модуль ядра и LSPosed — то есть без
root это недостижимо, и обещать такое в интерфейсе нельзя.

Что РАБОТАЕТ и уже есть у нас: исключить приложение из туннеля. Документация Android дословно —
«disallowed apps use system networking as if the VPN wasn't running». В режиме «только
отмеченные» неотмеченные приложения VPN уже не видят.

Осталось из этого пункта:
- [ ] написать правду в интерфейсе: спрятать VPN нельзя, но можно не пускать приложение в туннель;
- [ ] подсказка у правила «Прямо»: приложение вдобавок перестаёт видеть VPN;
- [ ] живой тест на устройстве: виден ли наш `tun0` через `NetworkInterface.getNetworkInterfaces()`
      на Android 11+ (документация молчит);
- [ ] поддержать системный экран исключений `ACTION_VPN_APP_EXCLUSION_SETTINGS` (Android 17+);
- [ ] отдельным заходом: сетевые признаки (MTU/MSS, TTL, отпечаток стека gvisor против системного),

  ни другое не блокируется — воспроизвести блокировку и убедиться, что проба её ловит, не удалось.

- `armeabi-v7a` не поставляется: ядер под эту архитектуру в AAR нет.


- **Обход DPI (byedpi/ciadpi) как sidecar.** Рекомендован **byedpi** (MIT, userspace SOCKS5, БЕЗ
  драйвера и UAC, кроссплатформенный) — Xray цепляется к нему через `dialerProxy`
  (`socks5://127.0.0.1:port`) и десинхронизирует именно соединение до Reality-сервера, когда DPI
  режет хендшейк; не конфликтует с wintun TUN. Схема — 1:1 как второе ядро (hysteria2). winws/WinDivert
  — опционально как «продвинутый» режим только под Windows, но тянет kernel-драйвер + предупреждения
  AV и дерётся с TUN → НЕ по умолчанию, с whitelist своего инстанса в `interference_scanner`.
- **Перебор ядер в автонастройке.** sing-box умеет не только hysteria2, но и VLESS/Reality, Trojan,
