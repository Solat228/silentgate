# Порт SilentGate на Android — дизайн

Дата: 2026-07-27. Статус: на согласовании.

Рабочий план задач — [ANDROID.md](ANDROID.md). Здесь — только
**решения и их обоснование**: что выбрано, из чего выбирали и почему отвергнуто остальное.

## Цель

Android-клиент с паритетом 1-в-1 по функциям и визуальному языку с Windows-версией 1.0.0.
Мобильная вёрстка — адаптированная (двухпанельный десктопный экран не переносится буквально),
но набор возможностей, названия, тексты, дефолты и краевые случаи — те же.

## В объёме

Все подсистемы Windows-версии: подписки Remnawave (XRAY_JSON, профили «Авто», notice-серверы,
мульти-подписки, логотип по cookie), два ядра (Xray + sing-box для hysteria2), TUN-захват,
split-tunnel (приложения/сайты, три действия), DNS-настройки, kill switch, `noRealIp`,
автопереподключение с fallback-серверами, двухфазный пинг, автонастройка с перебором вариаций,
сервис-чипы, 10 языков с RTL, отчёт поддержки, deep links, проверка обновлений.

## Вне объёма

- iOS, macOS, Linux (последующие этапы).
- M6 (Telegram-авторизация, личный кабинет, crypto-links) — делается позже и сразу
  кроссплатформенно.
- Изменения функциональности Windows-версии: рефакторинг общего кода не должен менять её
  поведение.

## Решение 1 — лицензионный режим: GPL-3.0 (вопрос закрыт)

**Что казалось проблемой.** `CLAUDE.md` и `STACK_DECISION.md` описывают закрытый коммерческий
продукт, из чего следовал запрет на линковку GPL; релиз 1.0.0 в `CHANGELOG.md` заявлял GPL-3.0.

**Проверка сняла вопрос.** В корне лежит настоящий файл `LICENSE` с полным текстом GNU GPL-3.0
(добавлен 26.07.2026, в день релиза 1.0.0), `README.md` §Лицензия утверждает то же. Файл лицензии —
это акт, а не оговорка в тексте: **проект под GPL-3.0**, а устарели `CLAUDE.md` и
`STACK_DECISION.md` (оба поправлены 27.07.2026).

**Обязанности:** производные под GPL-3.0; Corresponding Source того же тега доступен из того же
места, что APK, без платы (§6d), включая сборочные скрипты; тексты лицензий и атрибуция в поставке.
§6 «Installation Information» (анти-тивоизация) **не применяется** — она про передачу
потребительских *устройств*, а не про публикацию приложения.

## Решение 2 — датапуть TUN: `libbox`

**Что изменилось.** Пока проект считался закрытым, `libbox` был недоступен (линковка GPL), и
единственным путём оставался `hev-socks5-tunnel`. С подтверждением GPL-3.0 ограничение снято.

**Рассмотренные варианты.**

| Вариант | Вердикт | Почему |
|---|---|---|
| **`libbox`/sing-box принимает fd, делает TUN, форвардит в SOCKS 10808 → Xray** | ✅ выбран | архитектура **идентична Windows**; ~85 % генератора `singbox_config_builder.dart` переиспользуется; блокировка приложений работает; DNS-политика и `noRealIp` переносятся |
| `hev-socks5-tunnel` (MIT) + libXray + sing-box отдельным процессом | ❌ | лицензионно **ничего не экономит** (sing-box в поставке всё равно — он нужен для hysteria2), но отнимает блокировку приложений, всю DNS-секцию и `noRealIp` |
| Xray-native TUN (`xray.tun.fd`) | отложен | фича существует (v26.1.23), но README ядра предупреждает про «infinite network loop», per-app на Android нет из коробки, и переход выбросил бы ~85 % готового генератора |

**Контракт fd — инверсия управления:** ядро зовёт `PlatformInterface.OpenTun(options)`, приложение
строит `VpnService.Builder` по `TunOptions` и возвращает fd. Так работает официальный клиент
sing-box; другого поддерживаемого пути нет.

**Следствие:** порты 10808/10809/10085, `PortCheck`, `httpProxyPort` для сервис-чипов, статистика
обоих ядер, выбор ядра по `VpnServer.core` и приоритет источников конфига переносятся **без
изменений**. Xray остаётся обязательным: панельные профили «Авто» — это полные Xray-конфиги с
`balancers`/`burstObservatory`, sing-box их не переварит.

## Решение 3 — «Блок» для приложений: работает, но с Android 10

**Что казалось потерей фичи.** `VpnService.Builder` умеет только «в туннель» / «мимо туннеля».

**Решение.** С выбором `libbox` действие выражается правилом ядра
`{"package_name": [...], "action": "reject"}` — приложение идёт в туннель, ядро режет его
соединения. `AppAction.block` переносится 1-в-1.

**Ограничение:** матчинг по пакету опирается на `PlatformInterface.FindConnectionOwner()` →
`ConnectivityManager.getConnectionOwnerUid()`, доступный с **API 29 (Android 10)**. На более старых
версиях фича гейтится с явной пометкой в UI.

**Явно отвергнуто:** молча трактовать `block` как `direct`. Это превратило бы блокировку в
разрешение — дыра, а не деградация. Блокировка **сайтов** работает на всех версиях.

**Принятые щели матчинга** (не «чинить», покрыть тестами): приложения с общим UID матчатся
неточно (sing-box issue #3741); сокеты с `SO_BINDTODEVICE` дают `ProcessInfo == nil` и не
матчатся ни одним `package_name` (issue #4009).

## Решение 4 — структура форка

**Решение: один репозиторий, ветка `android`, один Flutter-пакет.** Платформенные части живут в
отдельных папках (`app/android/`, `app/lib/engine/android/`, `app/lib/ui/mobile/`,
`engine/android/`), общий код не дублируется.

**Отвергнуто: отдельный репозиторий или копия папки.** ~85 % кода общего; при двух копиях любая
правка Windows-версии обязана вручную повторяться в мобильной, и требование «паритет 1-в-1»
разрушается на первом же багфиксе. Форк-как-копия здесь не экономит работу, а создаёт постоянный
долг.

**Следствие:** порт — это не написание второго приложения, а **вычленение платформенного слоя**.
Основная работа Фазы 1 идёт в общем коде (разрыв прямых импортов `engine/windows/*`, вынос ~60 %
`WindowsEngine` в базовый класс), и её главный риск — регресс уже работающей Windows-версии.
Поэтому в критерии готовности вынесен отдельный пункт про непадение Windows.

## Решение 5 — где живёт движок

**Проблема.** На Windows движок живёт в процессе UI: окно закрыто — приложение в трее, процесс
жив. На Android процесс UI умирает независимо от VPN.

**Решение.** Движок — в foreground-сервисе с постоянной нотификацией (она же заменяет меню трея:
статус, трафик, кнопка «Отключить»). UI при повторном открытии переподключается к сервису и
восстанавливает потоки статуса и статистики.

Это единственное место, где архитектура расходится с Windows принципиально; всё остальное —
замена реализации под тем же интерфейсом `VpnEngine`.

## Решение 6 — geo-файлы

**Решение.** Скачивание при первом запуске с проверкой SHA-256 **плюс** урезанный набор в
`assets` как запасной. Чистое скачивание отвергнуто: первый запуск без сети превратил бы клиент в
кирпич. Полные 29 МБ в APK отвергнуты: половина бюджета размера.

Дополнительное следствие: связка «панель ↔ версии `.dat` у клиентов» становится опаснее — с
появлением Android появляется второй, более медленный цикл обновления. Порядок раскатки новых
категорий (сначала `.dat` в оба клиента, потом шаблон панели) зафиксирован в
`RU_ROUTING_SOURCES.md`.

## Решение 7 — канал дистрибуции влияет на код

Флейворы `sideload` / `store` вводятся сразу: самообновление через сторонний URL запрещено
политикой Google Play, а для APK-канала оно основной способ доставки. Вкручивать развилку позже
дороже, чем заложить сейчас.

## Риски, принятые осознанно

- **Блокировка приложений недоступна на Android 9 и ниже** (§3) — с явной пометкой в UI.
- **ICMP-пинг** на Android без root ограничен: либо реализация через `/system/bin/ping`, либо
  метод скрывается в настройках. Решается продуктово.
- **`json://`-ключи** построены на `String.hashCode`, нестабильном между платформами: при переносе
  данных с Windows импортированные JSON-конфиги могут осиротеть.
- **`ANDROID_ID` ≠ `MachineGuid`**: device-limit панели посчитает Android новым устройством, а
  factory reset — ещё одним.
- **Зависимость от апстрима sing-box выросла**: `libbox` — экспериментальный пакет (`experimental/
  libbox`), его API может меняться между минорными версиями. Отсюда пин на 1.13.x и проверка
  контракта при каждом бампе.
- **App Store и GPL-3.0 конфликтуют** (случай VLC) — всплывёт на этапе iOS, не на Android.
