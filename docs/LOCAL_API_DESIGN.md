# Локальный API SilentGate: клиент как прокси-сервер и управление из Python

**Дата:** 11.08.2026
**Статус:** согласовано владельцем, готово к плану реализации
**Платформа:** Windows сейчас, Android — следующим шагом (протокол проектируется общим)

---

## 1. Задача

Владелец хочет из Python-скрипта: гонять трафик через SilentGate, **выбирая для каждого
запроса конкретный выход** («этот запрос — через Германию, тот — через США, третий — напрямую»),
и управлять клиентом программно — подключить, отключить, сменить сервер, прочитать состояние.

### Что уже работает, а что мешает

Прокси-порты существуют: Xray всегда поднимает SOCKS5 на `127.0.0.1:10808` и HTTP на `10809`
(`core/xray/xray_config_builder.dart:13,78-104`). Порты фиксированы и не сдвигаются
`SILENTGATE_PORT_OFFSET`. Для стороннего кода это уже точка входа — но с тремя минами:

1. **Пароль случайный на каждую сессию и нигде не сохраняется** (`engine/engine_base.dart:131-158`).
   Скрипт получит 407 и не узнает почему. Постоянные креды можно задать руками в настройках —
   это единственный существующий способ.
2. **Порт живёт, только пока поднят VPN.** Ядро стартует в `startSession`, гасится в
   `teardownCore`. Режима «только прокси, без туннеля» в коде нет.
3. **Поведение зависит от режима захвата.** В режиме системного прокси (умолчание на Windows,
   `app_settings.dart:440`) пароль принудительно снимается — WinINET креденшелов не передаёт.
   То есть на умолчаниях порт открыт БЕЗ пароля, а после переключения на TUN тот же скрипт
   молча начинает получать 407.

Чтения состояния наружу нет вовсе. Управление есть, но одностороннее: url-схемы
`connect | disconnect | toggle | update` + `import`, ничего не возвращают вызывающему
(`core/url_scheme.dart:24-40`, `state/app_state.dart:576-627`). Режим «Авто (лучший сервер)»
снаружи недостижим в принципе.

### Ключевой рычаг, который уже есть

Мульти-VPN (1.2.0) разводит трафик через `inboundTag → outboundTag` в Xray. **Порт на выход
ложится ровно на эту механику:** ещё один inbound и ещё одно правило маршрутизации. Это не новая
подсистема, а расширение работающей.

## 3. Архитектура

Четыре независимые части. Первые две дают трафик, третья — управление, четвёртая закрывает
уже существующую дыру.

### 3.1. Режим захвата «Только прокси»

Новое значение `CaptureMode.proxyOnly` рядом с `tun` и `systemProxy`.

**Что делает:** поднимает ядро и локальные порты — и всё. Не создаёт TUN-адаптер, не пишет в
реестр WinINET, не требует прав администратора. Остальные программы машины ходят напрямую;
через VPN идёт только тот, кто явно целится в локальный порт.

**Почему это отдельный режим, а не «TUN без адаптера»:** в TUN-режиме туннель забирает весь
трафик машины (`auto_route` вешает `0.0.0.0/0` с метрикой 0), и пометка «Прямо» разбирается уже
внутри ядра. Здесь наоборот: ядро вообще ничего не перехватывает.

**Пароль в этом режиме ДЕЙСТВУЕТ.** Ограничение WinINET сюда не приходит — в порт смотрит не
системный резолвер, а конкретная программа, которая умеет передать логин и пароль. Значит
`systemProxyModeFor` (`engine/windows/windows_engine.dart:68-77`) обязан вернуть `false` для
`proxyOnly`, иначе порт откроется без пароля.

⚠️ **Сторож канала в этом режиме вооружается**, как и в остальных: проба ходит в
`127.0.0.1:httpProxyPort`, который здесь и есть основной порт.

⚠️ **Kill switch в этом режиме бессмыслен и должен быть недоступен.** Он держит трафик машины,
а машина здесь и так не в туннеле. Показывать включённый тумблер, который ничего не делает, —
ровно тот класс дефектов, за который в проекте платили дороже всего.

### 3.2. Порт на каждый выход

**Раскладка портов:**

⚠️ **ПОПРАВКА К МОДЕЛИ.** Именованной сущности «выход» (`VpnExit`, `AppSettings.exits`) в коде
НЕТ: она была и мигрирована (`app_settings.dart:689,746` — `_migrateExits`). Сейчас правило
раздельного туннелирования указывает **ключ сервера** (`AppRule.serverKey` / `SiteRule.serverKey`),
а тег outbound-а образуется из него — `exitTagFor(serverKey)` = `exit-<fnv32>`
(`core/singbox/exit_tags.dart`). CLAUDE.md в этом месте описывает прежнюю редакцию.
Поэтому «порт на выход» = **порт на СЕРВЕР**.

| Порт | Что это |
|---|---|
| 10808 / 10809 | Общий вход: трафик идёт по правилам раздельного туннелирования (как сейчас) |
| 10820 + n | Сервер №n из `AppSettings.apiExitServerKeys`, порядок — по возрастанию ключа |
| 10819 | «Прямо» — мимо VPN, реальный IP |

Диапазон `10820…10859` — до 40 серверов. Что сверх — порта не получает, и это пишется в журнал
(молча потерять сервер нельзя).

**Откуда берётся список.** Новая настройка `AppSettings.apiExitServerKeys` — ключи серверов,
которым пользователь явно выдал отдельный порт (выбираются в разделе «API для автоматизации»).
⚠️ Отдельная настройка, а НЕ «все серверы подписки»: сто серверов дали бы сто инбаундов в
конфиге ядра. И не «серверы из правил»: заводить фиктивное правило ради порта — костыль.

**Реализация.** Ключи из `apiExitServerKeys` подмешиваются в `ConnectionOptions.exitServers`
(`AppState._exitServers`, `app_state.dart:1587`) — там уже `Map<String, VpnServer>`. Дальше всё
работает само: `ExitOutbounds.build` собирает им outbound-ы с тегами `exitTagFor(key)`, а
построитель добавляет на каждый inbound `api-exit-<fnv32>` и правило
`inboundTag: [api-exit-<fnv32>] → outboundTag: exit-<fnv32>`.

**Порядок портов детерминирован:** ключи сортируются так же, как в `ExitOutbounds.build`
(`keys.toList()..sort()`). Иначе номер порта «дышал» бы между запусками, и скрипт с
захардкоженным портом уехал бы в другую страну.

⚠️ **Источник правды о живых выходах — `exitOutbounds` (`_liveExitTags`)**, а не список настроек.
`sing-box check` НЕ проверяет существование тега: конфиг со ссылкой на несуществующий outbound
принят настоящим ядром с кодом 0 и без вывода, а трафик молча уходит в `route.final`. Порт,
ведущий в несобравшийся выход, поднимать нельзя — иначе Python будет думать, что идёт через
Германию, а пойдёт через общий туннель.

⚠️ **Все новые порты проверяются `PortCheck` перед стартом** — как и остальные. Конфликт должен
называть процесс-держатель, а не падать с «Bad state».

⚠️ **Порт «Прямо» не обходит правила блокировки.** Он ведёт в `direct`, то есть мимо VPN, но
правила «Блок» к нему применяются — иначе служебный вход стал бы способом обойти собственные
запреты пользователя. Прецедент уже есть: `probe-in` на Android стоит ВЫШЕ пользовательских
правил, и именно поэтому закрыт паролем.

**Аутентификация портов выходов** — логин `sg` и **токен API** в качестве пароля.

⚠️ Именно токен, а НЕ креды основного прокси (`localInboundUser`/`localInboundPassword`), и это
не мелочь: в режиме системного прокси те креды принудительно пусты (WinINET их не передаёт), и
порты выходов оказались бы открыты любому процессу машины ровно на самом частом Windows-режиме.
На порты выходов WinINET не смотрит никогда — в них целится только явный клиент, умеющий
передать пароль, — поэтому ограничение системного прокси сюда не приходит и порт можно закрывать
всегда.

Следствие: **порты выходов — часть той же возможности «API для автоматизации»** и живут под тем
же тумблером и тем же секретом. Один тумблер, один токен, одно место в настройках. Выключен
тумблер — портов выходов нет, как нет и управляющего слушателя.

### 3.3. Управляющий API

**Транспорт:** HTTP/1.1 + JSON, `127.0.0.1:10870`, только loopback. Фиксированный порт — как и
остальные в проекте: рандомизация рассмотрена и отвергнута (`docs/BACKLOG.md:335-339`), потому
что фиксированный порт нужен диагностике и `PortCheck`.

**Включение:** тумблер «API для автоматизации» в настройках, **ВЫКЛ по умолчанию**. Выключен —
слушатель не поднимается вовсе.

#### Аутентификация

Заголовок `Authorization: Bearer <token>`. Токен постоянный, лежит в настройках, показывается
пользователю с кнопками «Скопировать» и «Обновить токен».

⚠️ **Постоянный токен на диске — осознанный размен, и его надо назвать вслух в интерфейсе.**
Случайный посессионный секрет безопаснее (`%APPDATA%\SilentGate` на Windows читается любым
процессом пользователя, в отличие от каталога приложения на Android), но скрипту нужен
предсказуемый ключ между перезапусками. Тот же размен уже сделан для своих логина и пароля
локального прокси и описан пользователю там же.

Три правила, взятые из уже случившихся в проекте аварий:

1. **Пустой токен = канал НЕ поднимается.** Не «поднимается без проверки». Правило уже
   закреплено тестом для прокси-инбаундов: логин при пустом пароле паролем не считается, инбаунд
   откатывается в `noauth` (`test/local_ports_closed_test.dart:78-84`). «Полумера опаснее
   отсутствия».
2. **Токен выдаётся в ОДНОЙ точке и ДО старта слушателя.** Секрет Clash API присваивался только
   внутри `buildSingboxJson`, то есть лишь на одном пути из нескольких, — и туннельный sing-box
   на Windows поднимал API без аутентификации для всех обычных подключений
   (`engine/engine_base.dart:182-193`). Тот же класс повторится, если токен проверять «где
   удобно».
3. **Запрос с заголовком `Origin` отвергается (403).** Локальный HTTP-порт без этого
   атакуется не только процессом на машине, но и любой открытой вкладкой браузера — sing-box с
   пустым секретом отдавал метаданные соединений с CORS `*`
   (`core/singbox/singbox_config_builder.dart:724-731`). Заголовков `Access-Control-Allow-*` не
   выдаём вовсе, preflight `OPTIONS` отвечаем 403.

#### Эндпоинты

Все — префикс `/v1`. Ответ всегда JSON. Ошибка: `{"error": {"code": "...", "message": "..."}}`.

| Метод | Путь | Ответ / тело |
|---|---|---|
| GET | `/v1/status` | `state` (`disconnected`/`connecting`/`connected`/`error`), `server`, `exit`, `captureMode`, `connectedSince`, `externalIp` |
| GET | `/v1/servers` | массив: `key`, `name`, `country`, `protocol`, `ping`, `working` |
| GET | `/v1/exits` | массив: `serverKey`, `name`, `country`, `port` |
| GET | `/v1/traffic` | `uplinkBytes`, `downlinkBytes`, `uplinkSpeed`, `downlinkSpeed` |
| GET | `/v1/subscription` | `title`, `usedBytes`, `totalBytes`, `unlimited`, `expiresAt` |
| POST | `/v1/connect` | тело `{"server": "<key>"}`, либо `{"name": "<имя>"}`, либо `{"auto": true}` |
| POST | `/v1/disconnect` | — |
| POST | `/v1/ping` | запускает пинг; отдаёт `{"started": true}` |

`POST /v1/connect` **умеет режим «Авто»** — дыру url-схем закрываем здесь, а не расширением
схем: `connectAuto` не вызывается сейчас ни из одной внешней ветки.

⚠️ **`server` — это КЛЮЧ сервера, а не имя.** Ключ (share-ссылка) стабилен и переживает
переименование на панели; имя панель меняет когда угодно, и скрипт, написанный по имени, тихо
сломается. `name` оставлен как удобство для ручных проб и отдаёт 409, если под имя подходит
больше одного сервера — молча выбрать первый значило бы подключить не туда.

**Коды:** 200 — успех; 400 — неверное тело; 401 — нет или неверен токен; 403 — присутствует
`Origin`; 404 — неизвестный путь; 409 — команда неприменима в текущем состоянии (например
`connect` без выбранного сервера); 500 — внутренняя ошибка с текстом.

#### Чёрный список: чего API НЕ отдаёт

Явным списком, а не «по умолчанию не отдаём»:

* пароль и логин локального прокси (`ProxyProbe.user`/`password` лежат в глобальных статиках —
  «отдать настройки» означало бы отдать ключ от туннеля);
* URL подписки целиком (последний сегмент пути у Remnawave — секрет; в отчёте поддержки он уже
  маскируется);
* содержимое конфигов ядра, `rawJsonOverride`, `rawPanelConfig`;
* токен самого API.

Страж — тест, который проходит по ВСЕМ ответам эндпоинтов и ищет подстроки из этого списка.

### 3.4. Закрытие порта 47654

`SingleInstance` слушает сырой TCP на `127.0.0.1:47654` и принимает произвольную строку без
аутентификации (`core/platform/single_instance.dart:10,19,26-39`). Любой локальный процесс может
послать `silentgate://connect?server=…` или подменить подписку — сегодня, без нового API.

В памяти зафиксировано решение владельца «риск подмены сервера через url-схемы принят как
незначительный» с обоснованием «браузер требует явного подтверждения перехода» и условием
пересмотра: «пересматривать, только если появится путь БЕЗ подтверждения пользователя». Порт
47654 — именно такой путь. Условие выполнено, владелец решил закрыть.

**Что меняется:**

* Строка, приходящая в сокет, разбирается на две категории: **передача ссылки при запуске
  второго экземпляра** (импорт подписки, `silentgate://import`) — работает как раньше, потому
  что её инициировал человек двойным кликом; **команды управления** (`connect`, `disconnect`,
  `toggle`, `update`) — требуют префикс с токеном.
* Формат: `<token>\n<url>`. Без токена или с неверным — команда отбрасывается, в журнал идёт
  строка с указанием, что команда отвергнута (молчание здесь неотличимо от «сделано»).
* ⚠️ **Второй экземпляр приложения обязан продолжать работать без токена.** Он передаёт ссылку,
  запущенную пользователем из браузера или проводника, и ломать этот путь нельзя.

## 4. Потоки данных

**Трафик через выход:**

```
Python (requests, proxies=127.0.0.1:10821)
   → inbound `api-exit-us` в Xray
   → правило inboundTag → outboundTag
   → outbound `exit-us`
   → сервер США
```

Раздельное туннелирование к этому пути **не применяется**: выход выбран явно, и применять поверх
него правила «этот сайт — прямо» означало бы игнорировать выбор вызывающего. Правила «Блок»
применяются (см. 3.2).

**Команда управления:**

```
Python → POST /v1/connect {"server": "..."} → проверка токена и Origin
   → AppState.toggleConnection / connectAuto
   → ответ 200 с новым состоянием либо 409 с причиной
```

**Чтение состояния:** API отдаёт то, что уже есть в `AppState` и движке; новых источников не
заводится. Выходной IP берётся из существующего `core/net/ip_info.dart` с кэшем — измерять его
на каждый `GET /v1/status` нельзя, это внешний запрос.

## 5. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Порт API занят | Слушатель не поднимается, тумблер в настройках показывает ошибку с именем процесса-держателя (`PortCheck` уже это умеет) |
| Порт выхода занят | Этот выход не получает порта; остальные работают; строка в журнал; `GET /v1/exits` отдаёт `port: null` |
| Выход не собрался | Порт не поднимается вовсе (см. 3.2) |
| `connect` при уже поднятом VPN | 200, состояние не меняется (идемпотентность) |
| `connect` без выбранного сервера и без `auto` | 409 с текстом |
| VPN выключен, запрос в порт выхода | Соединение отвергается — порта нет, ядро не поднято |
| Токен обновлён при живом API | Слушатель перезапускается с новым токеном; старые клиенты получают 401 |

## 6. Тестирование

**Юнит-тесты (обязательны, по правилу проекта — на каждую функцию):**

* `CaptureMode.proxyOnly`: `systemProxyModeFor` возвращает `false`; kill switch недоступен;
  конфиг не содержит ни `tun`-инбаунда, ни следов системного прокси.
* Порты выходов: на каждый живой выход есть inbound и правило; ссылка на несобравшийся выход
  порта не создаёт; переполнение диапазона логируется; порт «Прямо» ведёт в `direct`, но
  блок-правила к нему применяются.
* Токен: пустой → слушатель не поднят; неверный → 401; верный → 200; присутствует `Origin` → 403;
  `OPTIONS` → 403.
* Чёрный список: ни один ответ не содержит пароля локального прокси, полного URL подписки,
  токена API, содержимого конфигов. Тест перебирает ВСЕ эндпоинты, а не список руками.
* `SingleInstance`: команда управления без токена отвергается; с токеном выполняется; импортная
  ссылка работает без токена.
* Роундтрип настроек: новые поля (`apiEnabled`, `apiToken`, `captureMode.proxyOnly`) переживают
  запись и чтение; попадают в `reconnectReasons`, если влияют на конфиг ядра.

**Проверка конфигов ядром:** конфиг с портами выходов прогоняется через настоящий
`sing-box check` / `xray -test`, как это уже делается в `multi_exit_emit_test`.

⚠️ **`sing-box check` не проверяет существование тега** — целостность ссылок стережёт отдельный
тест, а не ядро.

**Живая проверка** (за владельцем, я VPN на хосте не включаю): в Hyper-V VM — три запроса из
Python в три разных порта одновременно, сверка трёх выходных IP; отключение VPN при живом
скрипте; обновление токена на живом API.

## 8. Границы

* **Только Windows.** На Android поднимать API этой работой не будем. Правило проекта: если для
  платформы аутентификация или изоляция недоступны, канал там не поднимается, а не поднимается
  «пока без пароля» (так уже поступили с api-инбаундом Xray, `readsXrayStats => false`).
* **Порт слушает только loopback.** Управление с другой машины не предусмотрено.
* **API не редактирует настройки.** Он умеет подключать, отключать, пинговать и читать. Правку
  раздельного туннелирования, подписок и выходов оставляем интерфейсу: это широкая поверхность,
  и она не нужна для заявленной задачи (YAGNI).
* **Режим «только прокси» не заменяет TUN.** Программы, не умеющие прокси, через него не пойдут —
  это его смысл, а не недостаток.
