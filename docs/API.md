# Локальный API для автоматизации

Windows-клиент умеет поднимать HTTP-API на `127.0.0.1`: читать состояние, переключать сервер и
отправлять трафик через конкретный выход прямо из скрипта — без интерфейса. Раздел настроек —
**Настройки → API для автоматизации**.

⚠️ Документ описывает то, что реально делает код (`core/net/api_ports.dart`,
`core/net/api_server.dart`, `state/api_handlers.dart`). Спека `docs/LOCAL_API_DESIGN.md` писалась
до реализации и местами шире того, что попало в код (например, в ответе `/v1/status` нет полей
`exit`/`connectedSince`/`externalIp`, а в `/v1/traffic` — `uplinkSpeed`/`downlinkSpeed`) —
сверяйтесь с этим файлом, а не с ней.

## Границы

* **Только Windows.** `AppState.applyApiSettings` гейтится буквальным `Platform.isWindows`. На
  Android локальные порты видит любое установленное приложение, отдельная модель угрозы для этого
  ещё не проработана — правило проекта: где нет изоляции, канал не поднимается вовсе.
* **Только loopback.** Слушатели биндятся на `InternetAddress.loopbackIPv4` — с другой машины в
  сети до них не достучаться, даже зная токен.
* **API ничего не настраивает.** Он подключает, отключает, пингует и читает. Правка раздельного
  туннелирования, списка подписок, состава выходов — только в интерфейсе.

## 1. Раскладка портов

```dart
// core/net/api_ports.dart
control     = 10870              // управляющий HTTP-API
direct      = 10819              // «Прямо» — мимо VPN, реальный IP
firstServer = 10820              // первый порт диапазона серверов
maxServers  = 40                 // 10820…10859
```

| Порт | Что это |
|---|---|
| `10870` | Управляющий API — статус, список серверов, переключение, отключение |
| `10820…10859` | По одному `mixed`-порту (SOCKS+HTTP в одном) на каждый сервер из настройки «серверы с отдельным портом» |
| `10819` | «Прямо» — трафик идёт мимо VPN, реальным IP. Полезен, чтобы сравнить «через VPN» и «без VPN» одной строкой кода |

⚠️ **Порядок в диапазоне 10820…10859 — часть контракта, не деталь реализации.** Ключи серверов
сортируются лексикографически (`[...keys]..sort()`), и порт — это позиция в отсортированном списке
плюс `10820`. Раскладка детерминирована между перезапусками ровно поэтому — но она **пересчитывается
заново** при каждом изменении списка «серверов с отдельным портом» в настройках. Добавили или убрали
сервер из этого списка — все порты правее него в отсортированном порядке сдвинулись. Поэтому
**не хардкодьте номер порта под конкретный сервер в скрипте** — спрашивайте `GET /v1/exits` и берите
`port` из ответа по `serverKey`. Сорок серверов — предел с запасом: каждый порт — это ещё один
inbound в конфиге ядра.

Сервер, который не входит в список выше 40-го по счёту, порта не получает. ⚠️ Это НЕ пишется в
лог приложения — такого вызова `AppLog` в коде нет, несмотря на то что раньше здесь было
обратное утверждение. Единственный способ узнать о переполнении — сравнить длину своего списка
«серверов с отдельным портом» с `GET /v1/exits`: сервер, оставшийся за диапазоном, в ответе
просто не появится (см. §5).

## 2. Включение и токен

Тумблер **выключен по умолчанию**: управляющий порт опаснее прокси-порта — он умеет переключать
сервер и читает состояние подписки. Кому он не нужен — у того ничего не слушает, и дыры нет.

Включение делает три вещи одновременно:

1. Появляется поле токена. Пустой токен — это не «открыто всем», это **канал не поднимается
   вовсе**: `LocalApiServer.start()` возвращает `false`, если `token.isEmpty`, ещё до попытки
   забиндить сокет.
2. Токен генерируется кнопкой «Обновить токен» (тот же генератор, что у паролей локального прокси)
   либо вводится руками — на диске он лежит открытым текстом в `silentgate_settings.json`.
3. В списке серверов подписки появляются чекбоксы «выдать порт» — отмеченные попадают в
   `AppSettings.apiExitServerKeys` и получают порт из диапазона 10820…10859 (см. §1).

Токен — **один на всё**: он же пароль управляющего API, он же пароль (логин `sg`) на каждом порту
выхода. Двух разных секретов в системе нет.

## 3. Два режима работы

Способ захвата трафика (**Настройки → Захват**) — не то же самое, что API, но от него зависит,
**когда порты выходов реально слушают**. Три значения `CaptureMode`, но для API важны два:

### «Обычное подключение» (TUN, `CaptureMode.tun`)

Стандартный режим клиента: TUN-адаптер забирает трафик всей машины (браузер, торрент-клиент,
что угодно) — обычная работа VPN, как без всякого API. **Поверх** этого, если тумблер API включён
и есть выбранные серверы, тот же TUN-инстанс sing-box дополнительно открывает порты 10820…10859:
скрипт, целящийся в конкретный порт, получает **другой** выход, чем остальная машина, не трогая
её маршрут. Порт «Прямо» (`10819`) в этом режиме — способ обратиться в интернет мимо туннеля, не
выключая VPN на остальной машине.

⚠️ Порты выходов появляются только когда сессия реально поднята (`connected`/`connecting`) — до
подключения слушать нечему, даже если токен задан и чекбоксы отмечены.

⚠️ **Правило «Блок» применяется и к порту сервера, и к порту «Прямо», без отдельной настройки.**
Гейт тот же, что у обычного раздельного туннелирования (`_userRulesActive` — в режиме «Всё через
VPN» правил, включая блок, нет вовсе), но если он открыт, заблокированный сайт/приложение режется
раньше маршрута на выход, каким бы портом ни воспользовался скрипт — иначе служебный вход стал бы
способом обойти собственные запреты (проверено тестом: `test/api_ports_test.dart`, группа
«Порт «Прямо»»).

### «Только прокси» (`CaptureMode.proxyOnly`)

Ядро поднимается, порты выходов слушают — и **больше ничего не происходит**: ни TUN-адаптера, ни
записи в системный прокси Windows. Остальные программы машины ходят в интернет как обычно, будто
VPN вовсе не установлен. Через VPN идёт **только** то, что явно обратилось в порт — 10808/10809
(общий вход, работает по правилам раздельного туннелирования, как всегда) либо конкретный порт
сервера/«Прямо». Это специально отдельный режим захвата, а не «TUN без адаптера»: ядро здесь в
принципе ничего не перехватывает, поэтому кладётся простой маршрутизатор без DNS-секции и без
tun-инбаунда (`core/singbox/exit_router_config_builder.dart`) — третий, отдельный процесс
sing-box, без прав администратора.

Это режим для автоматизации: поднять клиент фоном на машине, где VPN не должен трогать ничего,
кроме одного скрипта.

⚠️ **Порт «Прямо» поднимается в этом режиме, даже если не выбрано ни одного сервера под отдельный
порт** — он не зависит ни от `apiExitServerKeys`, ни от собравшихся `exitOutbounds`, единственное
условие — включённый тумблер API и непустой токен. До этого поведение было другим: маршрутизатор
выходов выходил рано при пустом списке серверов и не поднимал вообще ничего, включая «Прямо», —
починено, проверяйте по актуальному `_startExitRouter` в `windows_engine.dart`, если сомневаетесь.

Раздельное туннелирование в этом режиме не действует ни для одной программы (нечего перехватывать)
— поэтому по умолчанию оно не действует и для портов выходов, включая «Прямо». Правило «Блок» на
них можно включить отдельно (**Настройки → Захват → «Применять правила раздельного
туннелирования»**, `AppSettings.applyRulesInProxyOnly`, выключено по умолчанию, подпись из ARB:
«В этом режиме правила по умолчанию не действуют ни для одной программы. Включите, если хотите,
чтобы список «Блок» распространялся и на запросы через локальные порты»): кому нужна защита от
собственного же скрипта, включает галочку сам.

### Системный прокси (`CaptureMode.systemProxy`, умолчание)

⚠️ **В этом режиме порты выходов НЕ поднимаются вовсе** — ни при включённом тумблере API, ни при
отмеченных чекбоксах. Прописывать адрес в реестр WinINET и одновременно открывать явные порты — две
разные архитектуры (WinINET не передаёт креденшелы, и порт без пароля был бы дырой на самом частом
Windows-режиме), и вторая для системного прокси не реализована. Управляющий API (10870) при этом
работает как обычно — статус, список серверов, подписка, `connect`/`disconnect` доступны в любом
режиме захвата. Не получится только явно выбирать выход отдельным портом: `GET /v1/exits` вернёт
список с номерами портов, но слушателя на них не будет, и соединение до порта отвергнется.

**Итого:** нужны порты выходов — переключитесь на TUN или «Только прокси». Нужно только
управление и чтение состояния — работает при любом способе захвата, включая системный прокси.

## 4. Аутентификация и заголовки

* `Authorization: Bearer <токен>` — обязателен на КАЖДЫЙ запрос к управляющему API. Сравнение —
  в постоянное время (без раннего выхода по первому несовпавшему байту), чтобы не утекало через
  тайминг.
* Заголовок `Origin` в запросе → **403** ещё до проверки токена, даже если токен верный. Той же
  причиной отвергается `OPTIONS` (CORS preflight). См. §6 «Безопасность» — почему это не
  перестраховка.
* Заголовков `Access-Control-Allow-*` сервер не выставляет никогда.
* Ответ — всегда JSON, `Content-Type: application/json`.
* Тело POST — JSON-объект либо пусто (пустое тело у `disconnect`/`ping` — законный вызов без
  параметров). Битый JSON и JSON не-объект (массив, число, строка) — это разные вещи от пустого
  тела и оба дают `400`, не тихое `{}`.

Порты выходов (10819, 10820…10859) аутентифицируются **тем же токеном**, но по-другому: это не
HTTP, а `mixed`-inbound sing-box (SOCKS + HTTP в одном порту), логин `sg`, пароль — токен API.
Для `requests` это обычный прокси с basic-auth в URL — см. пример `proxies_for` в §8.

## 5. Эндпоинты

Базовый URL: `http://127.0.0.1:10870/v1`. Каждый пример ниже подставляет `$TOKEN` — переменная
окружения с содержимым `AppSettings.apiToken`.

### `GET /v1/status`

Состояние движка и текущего подключения.

```bash
curl -s http://127.0.0.1:10870/v1/status -H "Authorization: Bearer $TOKEN"
```

```json
{
  "state": "connected",
  "server": "Германия · VLESS",
  "captureMode": "tun",
  "connectedSeconds": 842
}
```

* `state` — `disconnected` / `connecting` / `connected` / `error` (имя `VpnConnectionState`).
* `server` — имя выбранного сервера (`displayName`) либо `null`, если не выбран.
* `captureMode` — `systemProxy` / `tun` / `proxyOnly` — см. §3.
* `connectedSeconds` — сколько секунд идёт отсчёт с момента, когда пользователь (или эта же API)
  **нажал подключиться**; `null`, пока не подключались. ⚠️ Не сбрасывается переподключением
  (обрыв, смена сети, сторож канала, перезапуск по правке настроек) — отвечает на вопрос «сколько
  я под VPN», а не «сколько живёт текущая сессия ядра». Сбрасывает только ручное отключение.

### `GET /v1/servers`

Все серверы активной подписки (не только те, что получили отдельный порт).

```bash
curl -s http://127.0.0.1:10870/v1/servers -H "Authorization: Bearer $TOKEN"
```

```json
{
  "servers": [
    {
      "key": "vless://…@1.2.3.4:443#Германия",
      "name": "Германия · VLESS",
      "country": "DE",
      "protocol": "vless",
      "pingMs": 46,
      "working": true
    }
  ]
}
```

`key` — стабильная share-ссылка сервера, а не его отображаемое имя (панель меняет имя когда
угодно). Именно `key` идёт в тело `POST /v1/connect`. `pingMs`/`working` — последний результат
измерения (`ProbeController`), обновляется по `POST /v1/ping` или ручному пингу в интерфейсе;
до первого замера оба поля `null`. `country` тоже может быть `null` — `FlagUtil.isoFromName`
достаёт код страны из имени сервера (обычно из флага-эмодзи в `remark`), и если панель имя без
такого флага не выдала, определить страну неоткуда.

### `GET /v1/exits`

Серверы, у которых есть отдельный порт, плюс запись «Прямо».

```bash
curl -s http://127.0.0.1:10870/v1/exits -H "Authorization: Bearer $TOKEN"
```

```json
{
  "exits": [
    {"serverKey": "vless://…#Германия", "name": "Германия · VLESS", "country": "DE", "port": 10820},
    {"serverKey": "vless://…#США",      "name": "США · VLESS",      "country": "US", "port": 10821},
    {"serverKey": null, "name": "Прямо", "port": 10819}
  ]
}
```

⚠️ **Список пуст (`{"exits": []}`), если API выключен в настройках или токен пуст** — гейт
`ApiPorts.exitsActive`, ровно тот же, что решает, создавать ли инбаунды физически
(`state/api_handlers.dart`, `exits()`). Если бы список отдавал порты при закрытом гейте, он
рекламировал бы адреса, на которых ядро никогда не поднимет слушатель. Это касается и записи
«Прямо» — при закрытом гейте её тоже не будет.

⚠️ **Сервер за пределами первых 40 (см. §1) в список не попадает вовсе — не отдаётся `port: null`.**
Раньше отдавался, и `proxies_for()` в `tools/silentgate.py` на такой записи собрала бы битый адрес
`http://sg:<токен>@127.0.0.1:None`; молчаливое исключение записи честнее заведомо нерабочего
адреса, выданного за рабочий. Запись «Прямо» от этого диапазона не зависит и не пропадает из-за
числа выбранных серверов.

Запись «Прямо» **не содержит поля `country`** (его нет в объекте вовсе, а не `null`) — это не
сервер, а служебный порт мимо VPN.

Даже когда гейт открыт и запись присутствует, это **раскладка портов из настроек, а не
подтверждение, что порт прямо сейчас слушает**: слушает то, что попадает под правила §3 (режим
захвата + активная VPN-сессия — порты выходов появляются только при `connected`/`connecting` в
TUN или при поднятом маршрутизаторе в «Только прокси»).

### `GET /v1/traffic`

```bash
curl -s http://127.0.0.1:10870/v1/traffic -H "Authorization: Bearer $TOKEN"
```

```json
{"uplinkBytes": 1048576, "downlinkBytes": 52428800}
```

Счётчики текущей сессии (обнуляются новым подключением), а не общий трафик по подписке — за ним
идти в `/v1/subscription`.

### `GET /v1/subscription`

```bash
curl -s http://127.0.0.1:10870/v1/subscription -H "Authorization: Bearer $TOKEN"
```

```json
{
  "title": "Мой тариф",
  "usedBytes": 12884901888,
  "totalBytes": 107374182400,
  "unlimited": false,
  "expiresAt": "2026-09-01T00:00:00.000Z"
}
```

`expiresAt` — ISO 8601 в UTC либо `null` (безлимитный срок). URL самой подписки сюда не попадает
никогда — см. §6.

### `POST /v1/connect`

Тело — ровно один из трёх вариантов:

```bash
# По ключу сервера — стабильный способ, рекомендуемый для скриптов
curl -s -X POST http://127.0.0.1:10870/v1/connect \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"server": "vless://…#Германия"}'

# По имени — только для ручных проб, панель меняет имена
curl -s -X POST http://127.0.0.1:10870/v1/connect \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"name": "Германия"}'

# Авто (лучший сервер) — то, что в интерфейсе кнопка «Авто»
curl -s -X POST http://127.0.0.1:10870/v1/connect \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"auto": true}'
```

Успех — `{"ok": true}`, `200`.

⚠️ **На уже живом канале `connect` меняет сервер, а не отключает VPN.** Раньше здесь стоял вызов
того же метода, что дёргает кнопка Connect в интерфейсе, — а это переключатель: на подключённом
канале он уходил в ветку отключения, и команда «подключись к серверу X» молча гасила VPN. Сейчас
`connect` на живом канале делает то же, что подсказка «переподключитесь» в интерфейсе:
отключает старую сессию и поднимает новую с сохранением отсчёта таймера — ответ тот же `{"ok": true}`,
но VPN остаётся включённым.

`server` без совпадения → `409 server_not_found`. `name`, под который подходит больше одного
сервера, → `409 ambiguous_name` (молча выбрать первый значило бы подключить не туда). Ни `server`,
ни `name`, ни `auto` → `409 server_required`.

### `POST /v1/disconnect`

```bash
curl -s -X POST http://127.0.0.1:10870/v1/disconnect -H "Authorization: Bearer $TOKEN"
```

`{"ok": true}` всегда, в том числе если VPN уже был выключен (идемпотентно).

### `POST /v1/ping`

Запускает пинг всех серверов подписки (тот же прогон, что кнопка пинга в интерфейсе) и сразу
возвращает `{"ok": true}` — результаты забираются потом через `GET /v1/servers`.

```bash
curl -s -X POST http://127.0.0.1:10870/v1/ping -H "Authorization: Bearer $TOKEN"
```

## 6. Коды ответов

| Код | Когда |
|---|---|
| `200` | Успех |
| `400 bad_request` | Тело POST — не JSON или не JSON-объект |
| `401 unauthorized` | Заголовка `Authorization` нет либо токен неверный |
| `403 browser_not_allowed` | В запросе есть заголовок `Origin`, либо метод `OPTIONS` |
| `404 not_found` | Неизвестный путь |
| `409 <code>` | Команда неприменима сейчас: `server_not_found`, `ambiguous_name`, `server_required` |
| `500 internal` | Внутренняя ошибка (в том числе — сработавший барьер секретов, см. §6.1) |

Ошибка — всегда `{"error": {"code": "...", "message": "..."}}`.

### 6.1. Барьер секретов

Тело каждого ответа перед отправкой в сокет проверяется на присутствие запрещённых полей
(`core/net/api_secrets.dart`). Если обработчик по ошибке положил в ответ что-то из чёрного списка
— наружу вместо честных данных уходит `500 internal` с текстом «Ответ заблокирован», а само
событие пишется в `app.log` уровнем ERROR. Это забота транспорта, а не отдельного эндпоинта: барьер
стоит на границе, откуда уходит **любой** ответ, а не только те, что явно его вызывают.

## 7. Безопасность

Это не факультативный раздел — прочитайте его, прежде чем включать тумблер.

### Что получает держатель токена

Токен — единственный секрет системы. С ним можно:

* переключать активный сервер и режим «Авто», отключать VPN;
* читать состояние: какой сервер выбран, идёт ли подключение, сколько длится сессия;
* читать остаток и срок подписки (`title`, `usedBytes`, `totalBytes`, `expiresAt`);
* пускать любой трафик через любой из выданных портов выхода — то есть пользоваться VPN-туннелем
  как своим.

Токен не даёт: менять настройки, добавлять/удалять серверы или подписки, читать URL подписки,
пароль локального прокси или содержимое конфигов ядра (см. §7.3).

### Токен на диске — открытым текстом

`AppSettings.apiToken` лежит в `%APPDATA%\SilentGate\silentgate_settings.json` без шифрования и
попадает в любую резервную копию этой папки. Это **осознанный размен**, а не недосмотр: случайный
секрет на каждую сессию был бы безопаснее, но тогда скрипт не смог бы держать постоянный ключ
между перезапусками приложения — а именно это нужно для автоматизации. Тот же размен в проекте уже
сделан для логина и пароля собственного локального прокси (`localProxyUser`/`localProxyPassword`)
по той же причине.

Практические следствия:

* **не коммитьте токен в общий репозиторий** и не кладите его в файлы, которые синхронизируются
  куда-то ещё, кроме личной машины;
* держите его так же, как любой другой пароль от собственного сервиса — в переменной окружения
  или локальном секрет-хранилище скрипта, не в тексте программы;
* кнопка «Обновить токен» в настройках выдаёт новый секрет и сразу перезапускает слушатель — старые
  клиенты после этого получают `401`, если пароль стоит перевыпустить.

### Почему запросы из браузера отвергаются — и это не перестраховка

Любой локальный порт **без проверки `Origin`** доступен не только процессам на машине, но и
**любой открытой вкладке браузера**: JavaScript со страницы может обратиться на `127.0.0.1:10870`
так же свободно, как на собственный сервер сайта — токен браузер не знает, но факт «порт открыт
локально» сам по себе достаточен для CSRF-подобной атаки на конфиг ядра, если бы порт отвечал без
проверки. `LocalApiServer` отклоняет любой запрос с заголовком `Origin` **до** проверки токена —
браузер прикладывает этот заголовок к каждому кросс-доменному (а для некоторых методов и
однодоменному) запросу сам, без спроса у страницы, а обычные HTTP-клиенты (`curl`, `requests`,
`urllib`) его не шлют вовсе. Это и есть граница между «программируемый доступ с этой же машины» и
«любая открытая вкладка». Ответных заголовков `Access-Control-Allow-*` сервер не выдаёт ни при
каких условиях — так у браузера нет ни одного законного пути прочитать тело ответа, даже если бы
запрос как-то прошёл.

Тот же класс дыры уже случался в проекте: sing-box с пустым секретом Clash API отдавал метаданные
соединений с CORS `*` любой странице — отсюда и урок.

### 7.3. Чего API не отдаёт никогда

Явный список в `core/net/api_secrets.dart`, проверяемый на каждом ответе (см. §6.1), а не «по
умолчанию не отдаём» — обработчик мог бы забыть про новое поле, а барьер поймает его одинаково:

* пароль и логин **локального прокси** (`localProxyPassword`/`localProxyUser`) — это ключ от
  туннеля целиком, включая обход правил «Блок»;
* **URL подписки** (`subscriptionUrl`) — последний сегмент пути у Remnawave это токен доступа к
  панели, а не просто адрес;
* **содержимое конфигов ядра** (`rawJsonOverride`, `rawPanelConfig`) — там те же креды серверов,
  что и в самой подписке;
* **сам токен API** (`apiToken`) — токен не возвращается ни одним эндпоинтом, включая `/v1/status`
  и тексты ошибок.

### 7.4. Порты серверов закрыты тем же токеном, не отдельным паролем

⚠️ У каждого порта выхода (10819, 10820…10859) нет собственного секрета — пароль там **токен API**
(логин `sg`). Это значит: обновили токен в настройках — обновился пароль сразу у всех портов
выхода одновременно, старые клиенты со старым паролем получают отказ на каждом из них, а не только
на управляющем порту. Отдельного «пароля для трафика» в системе нет и не планируется — это
преднамеренно один секрет на весь канал.

## 8. `tools/silentgate.py`

Рабочая обёртка без зависимостей, кроме `requests`. Токен и порт берутся из настроек приложения
(**Настройки → API для автоматизации**, кнопка «Скопировать пример для Python» отдаёт уже
заполненный фрагмент).

```python
from silentgate import SilentGate

sg = SilentGate(token="...")
print(sg.status())                 # {'state': 'connected', 'server': 'Германия · VLESS', ...}

for e in sg.exits():
    print(e["name"], "->", e["port"])

sg.connect(server_key="vless://…#Германия")   # или auto=True
sg.disconnect()

# Прокси-словарь под конкретный выход — для requests:
proxies = sg.proxies_for("vless://…#Германия")
r = requests.get("https://api.ipify.org?format=json", proxies=proxies)

# None — порт «Прямо» (мимо VPN, реальный IP), для сравнения с/без туннеля:
direct = sg.proxies_for(None)
r_direct = requests.get("https://api.ipify.org?format=json", proxies=direct)
```

⚠️ `proxies_for` **не хардкодит номера портов** — он читает их из `GET /v1/exits` на каждый вызов
и ищет нужный `serverKey`. Раскладка портов пересчитывается при изменении списка «серверов с
отдельным портом» (см. §1); скрипт, который сам присвоил себе номер порта, рано или поздно
подключился бы не туда. ⚠️ Если гейт API закрыт (см. §5) или искомого сервера нет в диапазоне,
`exits()` вернёт список без нужной записи — `proxies_for` в этом случае бросает **`KeyError`** с
понятным текстом, а не собирает битый адрес из отсутствующего порта.

### Обработка ошибок

Сервер API отвечает на отказ ВСЕГДА одним и тем же JSON-телом — `{"error": {"code", "message"}}`
(см. §6) — и `_get`/`_post` разбирают его сами: любой ответ не `200` поднимает **`SilentGateError`**
с полями `.code` и `.message`, а не голый `requests.HTTPError` (у того нет причины отказа, только
код и текст HTTP). Ловите его:

```python
from silentgate import SilentGate, SilentGateError

try:
    sg.connect(server_key="vless://…#несуществующий")
except SilentGateError as e:
    print(e.code, e.message)   # 'server_not_found' 'Сервер не найден'
```

`requests.HTTPError` из `_raise_for_error` всплывает, только если тело ответа НЕ разобралось как
`{"error": ...}` — с настоящим `LocalApiServer` такое не случается (он всегда отвечает этим
форматом на ошибку, барьер секретов из §6.1 тоже отдаёт `{"error": ...}`), это защитный код на
случай, если между скриптом и портом окажется прокси или файрвол, подменяющий тело ответа.
Сетевые сбои (порт закрыт, неверный `host`, таймаут) — это `requests.ConnectionError` /
`requests.Timeout`, отдельная категория, `SilentGateError` их не покрывает.
